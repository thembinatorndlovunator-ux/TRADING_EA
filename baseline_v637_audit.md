## Fractal support and resistance

- **FACT.** Fractal detection is `IsSwingHigh`/`IsSwingLow` (lines 4844, 4858), a symmetric N-bar-either-side test with depth `MathMax(2, InpFractalDepth)` or `MathMax(2, InpStructureSwingDepth)` depending on caller. `FindLastTwoSwingIndexes` (4872) and `FindRecentSwingHigh`/`FindRecentSwingLow` (4897, 4905) walk these fractals.
- **FACT.** The actual SR-zone builder is `FindSRZone` (5055–5131). It scores each candidate swing level by: touch count capped/decayed via `InpSRTouchDecayAfter`/`InpSRTouchDecayPenalty` (lines 5099–5103, inputs 252–253), an H4-confluence bonus/penalty via `HasHTFLevelNear` (5107–5111, 7360), a reaction-quality score `SRReactionScore` (5210), a recency term, and a distance penalty (5113). `InpSRMinTouches` (242, default 2) is a hard cutoff (5085–5086). `RefineSRClusterLevel` (5153) re-centers the level on a recency/rejection-weighted average of wick touches rather than the raw first-found fractal (5075–5076 when `InpSRSnapLineToWickCluster` is on).
- **FACT.** `LevelInvalidated` (7051) retires a level after `InpSRInvalidationCloses` (174, default 2) consecutive closes beyond it — checked inside `FindSRZone` (5091) and again inside `FindClusterBoundary` (7926).
- **COMMENT-CLAIMED, checks out (citation corrected per independent review).** `ApplyConfirmedSupportResistanceGate` (1992) enforces the "second distinct retest" rule via `HasSecondRetestConfirmation` (6991–7019), which requires two separated touches **total** — normally one prior touch plus the current bar's closed retest (`current_bar_is_touch && touches >= 2`, 7017–7019) — not two prior touches plus the current retest as an earlier draft of this audit stated. This is genuinely enforced for both intact-level bounces (2083, 2134) and role-reversal (flipped) levels (2059, 2113) — confirmed by reading both branches of the gate.
- **CONTRADICTION (fractal-depth fragmentation).** The comment at line 201 (`InpStructureSwingDepth`) says this single input is "used by SR, structure, and FVG checks," implying one unified fractal definition. In fact three independent inputs all default to 2 but are never synchronized: `InpFractalDepth` (155, drives the dealing range / premium-discount fractals in `GetConfirmedDealingRange`), `InpStructureSwingDepth` (201, drives `FindSRZone`, `FindClusterBoundary`, FVG structure checks), and `InpTrendSwingDepth` (309, drives `BuildThreePointTrendLine` for the TrendFollowing strategy, line 6331). An optimizer or a hand-tune of one without the others silently desynchronizes what "a confirmed fractal" means between subsystems that the comment claims share a single definition.
- **HYPOTHESIS.** `InpSRZoneTolerancePoints` (1500 points, line 237) vs. the ATR-based zone (`InpSRUseATRZone`, `InpSRATRZoneMultiplier=0.20`, lines 238–239, resolved in `GetSRZoneTolerance` 5241) can produce very different practical zone widths across symbols with different point values (e.g. synthetic indices vs. FX pairs); whether the ATR path ever produces a degenerate (too-wide or too-narrow) zone in practice needs live data, not just a code read.

  2. `EvaluateTrendBreaker` (2562) — a three-point trendline (`BuildThreePointTrendLine`, 6315) on H1/H4, broken by a 3-candle rule (`ThreeCandleBreak`, 6388) plus MA-cross/MACD/TSMOM confirmation.
  3. The dedicated H1 trendline strategies: `BuildTrendlineTouchSignal` (7573) and `BuildTrendlineBreakRetestSignal` (7663), both built on `BuildThreePointTrendLine(InpTrendlineTF, …)`.
  This is functioning but duplicated logic — three separate "what is a trendline / has it been touched or broken" implementations with different depth inputs, contributing to the file's overall complexity (see "excessive complexity" below).
- **COMMENT-CLAIMED, checks out.** Line 314: `InpEnableTrendlineTouch = false // OFF by default per its lifetime journal record`. ## FVG retests

- **FACT.** The FVG pipeline is `IsFVGMiddleCandleDisplacement` (1474) → `FindFreshRetestedFVG` (1517) → `FindFVGLinkedBreakOfStructure` (1557) → `HasFVGM15StructureContext` (1588) → `HasFVGM5Confirmation` (1619) → `BuildFVGRetestSignal` (1662).
- **COMMENT-CLAIMED, checks out.** The comment at 1527 ("newest to oldest so two valid gaps cannot produce an arbitrary old entry") and 1488 ("first quality return to a fresh imbalance") are both enforced: `WasFVGTouchedBeforeCurrentRetest` (1484) invalidates any gap that was touched by any bar strictly between formation and the current bar (1489–1494), and `FindFreshRetestedFVG`'s loop starts at the newest bar (`i=3` ascending from the most recent index, per the array's series ordering) and returns on the first qualifying match (1550–1552).
- **FACT.** Three independent structural requirements gate the FVG entry, all default ON: `InpFVGRequireBreakOfStructure` (207) via `FindFVGLinkedBreakOfStructure`; `InpFVGRequireM15Structure` (209) via alignment-or-recent-shift-or-BOS (1606–1609); `InpFVGRequireM5Confirmation` (210) via `HasFVGM5Confirmation` (1619), which itself requires a **post-retest** touch (1636, `entry[i].time < m15_retest_time → continue`) plus a directional close and rejection candle (1650–1659).
- **FACT.** `BuildOBConfluenceSignal` (8477) reuses the FVGRetest strategy bucket (`signal.strategy = "FVGRetest"`, line 8543) for M30-order-block trades, so the journal's per-strategy win-rate learning (`ApplyLearningToScore`) cannot distinguish "plain FVG retest" performance from "M30 OB + SR confluence" performance — both feed the same `g_strategy_wins[STRAT_FVG]`/`g_strategy_trades[STRAT_FVG]` counters (3592–3599, matched by `StringFind(strategy, "FVGRetest")`). A run of losing OB-confluence trades will depress the score of ordinary FVG retests and vice versa.

It requires both a resistance and a support cluster boundary (7957–7960), a minimum range height in ATR (`InpRangeMinHeightATR`, 266), and exits at `InpRangeExitPercent` (267, default 90%) of the way to the opposite boundary rather than at a fixed R-multiple (7986, 8006).
- **COMMENT-CLAIMED, checks out.** The V6.31 design note at lines 8106–8115 explicitly states rotation trades sell/buy "even against the H1 trend... at reduced risk." Verified: `BuildRotationSignal` (8116) never calls `GetDealingRangeTrend()` as a directional gate (only `InpRotationBlockVsM15Trend` checks the *M15* responsive trend, line 8143, which is a much shorter-term read than the H1 dealing-range trend) — so an H1-trend-opposing Rotation trade is genuinely possible by design. Reduced risk is enforced in `CalculateVolumeForRisk` via `g_rotation_sizing` and `InpRotationRiskFactor` (278, default 0.75×) at lines 2812–2818.
- **FACT / policy-ambiguity (heading label corrected per second-pass review — not a contradiction).** `IsSelfConfirmedSetup` (7534–7541) explicitly lists `"ROTATION_"` as a self-confirming setup that should bypass the horizontal SR/premium-discount gates (and it does — `ApplyPremiumDiscountFilter` line 1895 and `ApplyConfirmedSupportResistanceGate` line 2001 both skip it). However, `ApplyRegimeRouting`'s Volatile Expansion branch (7513–7526) hard-blocks **any** setup that is not in its own `breakout_setup` string list (7475–7482: `"Breakout"`, `"TrendBreaker"`, `"OuterRange"`, `"Break_CHoCH"`, `"BreakRetest"`, `"BOS_Retest"`, `"OB_SR_"`, `"NFP_"`) and does not contain `"FVG"`. Rotation setups are literally named `"ROTATION_PremiumSell"` / `"ROTATION_DiscountBuy"` (8212, 8281) — they match **none** of those strings, and do not appear in `mean_reversion_setup`'s list either (7471–7474 only lists `"SR_Bounce"`, `"SR_FalseBreakoutTrap"`, `"SR_ChannelBoundary"`, `"RANGE_Cycle"`). The result: during Volatile Expansion regime, a Rotation trade that already passed its own self-confirmation is vetoed by the regime router — **narrowed, fifth-pass review: "silently" overstated this; precisely, it is journal-silent always, and dashboard-visible only in the narrow global no-survivor condition described below** — with reason `"No trade: expansion regime accepts only breakout or FVG continuation setups"` (7524) — even though nothing in `BuildRotationSignal` itself prevents it from firing during that regime (it has no internal `CurrentMarketRegime()` check, unlike `BuildRangeCycleSignal`). **Characterization: a verified, reachable interaction between two independently-documented rules, not a demonstrated maintenance oversight.** "Self-confirmed" is documented in this file as bypassing the value-area/SR *confirmation* gates specifically, not as a guarantee of bypassing regime *policy*. The **V6.31 Rotation design note** (lines 8106–8115 — **name corrected in fifth-pass review, was mislabeled "Volatile Expansion design note"**) does not itself say Rotation should be allowed to trade during Expansion — it only motivates Rotation's own qualified, reduced-risk countertrend behavior in general — so whether excluding Rotation from the expansion allow-lists was an intentional policy (mean-reversion setups generally shouldn't fire into an expanding market) or an oversight cannot be determined from the source alone; both readings are consistent with what's written. **Dashboard-visibility condition corrected, fourth-pass review — the earlier framing of this was wrong twice, so stated precisely here:** `g_last_value_filter_reason` (set at line 7524 when Rotation is vetoed) is reset to empty at the *start* of every candidate's evaluation (`ApplyPremiumDiscountFilter`, line 1889) and only read back out at the dashboard layer inside `BuildCombinedSignal`'s check `if(!best_buy.valid && !best_sell.valid)` (lines 885–890) — i.e., the condition is **global across both directions**, not "Rotation was the only candidate in its own direction" as earlier drafts of this audit claimed. This should be recorded as a **verified reachability/policy-ambiguity finding that needs an explicit specification decision** (should Rotation be allowed during Expansion or not?) **and backtest evidence** to assess impact — not asserted as a proven bug or a proven correct policy. **Severity: depends on the specification decision** — matters operationally only if Rotation-during-Expansion was actually intended to trade.

## Pilot trade and add-ons

- **FACT.** `PilotStage()`/`SetPilotStage`/`UpdatePilotTrendState` (6916, 6923, 6933) implement a 3-state machine (0=needs pilot, 1=pilot open/awaiting confirmation, 2=confirmed/full sizing) keyed per-symbol via global variables (`PilotStageKey`, 6901). A trend change (`GetDealingRangeTrend()` differs from the stored trend) resets to stage 0 (6940–6945).
- **FACT.** `CalculateVolumeForRisk` (2803) uses the broker minimum lot for the pilot trade (2865–2882), gated by `InpPilotMaxActualRiskPercent` (110, default **5.0%**) — this is a materially larger actual-risk allowance than the standing `InpRiskPercent`/`InpMaxRiskPercent` (79–80, default 1.0%/2.0% of equity).
- **FACT — directly answers "risk that changes based on a weak sample."** The pilot trade is, by construction, the *least*-confirmed trade of a new trend (that is its entire purpose — it exists precisely because the trend hasn't proven itself yet). Yet it is allowed up to 2.5–5× the actual-risk percentage of a normal, fully risk-budgeted trend-confirmation trade. This is backwards from a "size down when uncertain" philosophy — the EA takes objectively *more* real-money risk on its least-proven signal in order to satisfy the broker's minimum-lot floor.
- **COMMENT-CLAIMED, checks out.** Input 117 (`InpAddOnOnlyWhenInProfit = true // never average down: add only while every open trade is in profit`) and the header comment at line 8083–8087 ("add-ons must be same-direction and spaced by favorable movement") are enforced, but the "in profit" half of the guarantee is enforced in a *different* function than the one the map flagged: `AddOnConditionsMet` (8058) only checks (a) same-direction (8083–8087) and (b) `InpAddOnMinSpacingATR` (119) of favorable movement since the last entry (8089–8099) — it does **not** itself check that all open trades are profitable. That check lives in `OnTick` (line 608): `if(our_positions > 0 && InpAddOnOnlyWhenInProfit && AnyOurPositionInLoss()) return;`, using `AnyOurPositionInLoss()` (7554). Both pieces together do implement "never average down," but this is split across two functions and gated by two separate inputs (`InpAddOnOnlyWhenInProfit` could be turned off independently of `AddOnConditionsMet`'s spacing rule), so the comment's guarantee is **conditional on `InpAddOnOnlyWhenInProfit` staying true** — turning it off silently removes the "no averaging down" protection while add-ons keep firing on spacing alone.
- **FACT.** `EffectiveMaxPositions` (7543) only allows more than 1 position when `PilotStage() == 2` (confirmed), capping additional exposure at `InpMaxConfirmationAddOns` (116, 0–2).

## Regime-aware score adjustment

- **FACT.** `CurrentMarketRegime` (7425) is a 3-way classifier (Trending / Ranging / Volatile Expansion), cached per entry-TF bar (7427–7429), computed from ATR-expansion-over-average (`InpRegimeExpansionATRFactor`, 143) outranking a simple `GetDealingRangeTrend() != 0` trend check (7435–7439).
- **FACT.** `ApplyRegimeRouting` (7464) applies hard-coded priors (7484–7527) — block counter-trend mean-reversion in Trending regime (7488), boost mean-reversion / penalize momentum in Ranging regime (7504–7511), and restrict Volatile Expansion to breakout/FVG setups only (7513–7526) — layered on top of the learned regime statistics applied separately in `ApplyLearningToScore` (3676, regime block at 3711–3739).
- **COMMENT-CLAIMED, checks out (with the caveat above).** V6.37's changelog claim "the regime bench needs 10 samples before zeroing anything" (line 45) is verified: `InpRegimeLearningMinTrades` (137, default 10) gates the regime-bench check at line 3720 (`if(g_regime_trades[s][regime] < MathMax(2, InpRegimeLearningMinTrades)) continue;`).
- **Verified policy/reachability choice, not a confirmed bug (see Range-Cycle/Rotation section above for the corrected characterization).** `ApplyRegimeRouting`'s Volatile Expansion branch blocks `ROTATION_*` setups despite them being flagged self-confirmed elsewhere in the same file; whether this is an oversight or an intentional policy that Rotation shouldn't trade during Expansion is a specification question, not something this static read can settle.
- **HYPOTHESIS (self-reinforcing lock, mechanism is FACT, real-world severity is not).** Once `InpBenchLosingStrategies` (140, default true) fires for a strategy-in-regime combination (win rate < `InpBenchWinRateThreshold`=40% with net loss and ≥10 samples), `ApplyLearningToScore` returns a hard `0.0` score for every future candidate of that strategy in that regime (line 3727). Because `SelectBestIndependentSignal` only ever trades the single highest-scoring signal per direction, and a benched strategy's score is forced to 0 (below `InpMinimumSignalScore`=70), it can never again win a direction slot in that regime — and therefore can never log a new trade there to update its own statistics. This is a structurally self-perpetuating lockout: the only way out is for `CurrentMarketRegime()` to reclassify the *same* market conditions into a different regime bucket in the future. Whether this actually traps a strategy for long stretches, or whether regime reclassification happens often enough to be a non-issue, requires backtest/live evidence — but the trap mechanism itself is directly readable in the code.

Separately, `CloseAllOurPositions` (3389–3414), which executes when the daily lock trips (`InpClosePositionsAtDailyLimit`, 125), has **two loops with inconsistent filtering**: the position-closing loop (3391–3400) checks only the magic number, while the pending-order-deletion loop directly below it (3403–3413) checks **both** magic number *and* `OrderGetString(ORDER_SYMBOL) != _Symbol`. Whether the *intended* design was per-symbol isolation (as the version-history comment for a different subsystem claims — line 6: "per-symbol journal/learning isolation"; the explicit V6.10 fix in `OnTradeTransaction` at lines 676–681, which is a distinct piece of code from the daily-limit path) or an account-wide magic-scoped lock is a specification question this file does not answer for the daily-limit subsystem specifically; either way, the two loops inside `CloseAllOurPositions` disagree with each other, which is the concrete, unambiguous defect. **Severity: yes, matters for live/multi-symbol deployment.**
- **Qualifications confirmed by independent review — preserve both.** (1) All four daily money/percent thresholds (`InpDailyProfitTargetMoney`/`Percent`, `InpDailyLossLimitMoney`/`Percent`, lines 120–123) **default to zero**, meaning this dangerous path is disabled out of the box; it only activates if an operator sets a real threshold. If an account-wide daily lock across same-magic instances was the actual intent, then force-closing positions on every symbol sharing that magic on trip is *consistent* with that intent, and the genuinely inconsistent piece is that the **pending-order deletion loop is scoped to `_Symbol`** while the position-closing loop is not — the two loops disagree with each other regardless of which scope was intended. The specification must state explicitly which scope (per-symbol or per-magic-account-wide) is correct before this is "fixed" in a new engine, rather than assuming per-symbol was always the goal.
- **HYPOTHESIS (restart/instance divergence).** `SetupDailyState` (3260–3265) initializes `g_day_start_equity` from the account equity at the moment of that call. ## ATR-based stop floors and caps

- **FACT.** `GetInitialStopBuffer` (5739) and `EffectiveATRStopMultiplier` (5752) compute the *entry* buffer; separately, `ApplyMinimumStopDistance` (8805) enforces the V6.35 "breathing room" floor of `InpMinStopDistanceATR` (86, default 1.50) × M15 ATR (`InpStructureTF`, 8810), only ever widening, never tightening, a signal's stop (8816–8819, matching the comment at 8798–8804).
- **COMMENT-CLAIMED, checks out.** The V6.36 fix comment (line 39–41, and again at 5876–5878) claims the stop *cap* now measures on the same timeframe (M15/`InpStructureTF`) as the floor, "so confirmed entries stop being rejected." Verified: `GetMaximumStopDistance` (5863) computes its ATR-based component using `GetATR(_Symbol, InpStructureTF, ...)` (line 5879) — the same timeframe as `ApplyMinimumStopDistance`'s floor. This specific historical bug (measuring the cap on the M2–M5 entry TF while the floor was on M15) is genuinely fixed.
- **CONTRADICTION (unit mismatch between floor and cap survives the V6.36 fix).** `GetMaximumStopDistance` (5863–5886) takes `MathMin` of up to three components: a fixed-points cap (`InpMaxSLPoints`, disabled by default), a **percent-of-entry-price** cap (`EffectiveMaxSLPercent()`, 5868–5872, default 2.0% / 5.0% for gold), and the ATR-based cap (2.5× / 6.0× M15 ATR). The floor (`ApplyMinimumStopDistance`) is purely ATR-based (1.5× M15 ATR) with no percent-of-price equivalent. Because the percent-of-price cap and the ATR floor are measured in genuinely different units, there is no guarantee that `1.5 × M15\_ATR ≤ 2.0\% × price` holds for every symbol/session — on a symbol or during a period where M15 ATR is large relative to price (which is common for point-heavy or thin-book synthetic instruments), the floor can legitimately exceed the percent-based cap. When that happens, `ApplyStopDistanceCaps` (5820) — which runs *after* `ApplyMinimumStopDistance` in `OpenSignal` (lines 2716→2718) — will, by default (`InpSkipTradeWhenSLTooWide=true`, line 95), simply **reject the trade** rather than resolve the conflict, unless the signal also clears the "elite setup" bar (`InpEliteScoreForWideStop`, 212, score ≥ 85) which permits up to `InpEliteMaxSLMultiplier` (213, 2.0×) the cap. This is a real, arithmetic-level conflict between two safety features that are individually well-intentioned but not jointly validated against each other; whether it manifests often enough to matter needs per-symbol backtest data (see the dedicated section below).
- **FACT.** `EffectiveATRStopMultiplier` (5752) widens the ATR multiplier by +0.15 when current ATR exceeds 1.25× its 80-bar average (5757), and by a further +0.10 whenever `OverallWinRate()` sits between 0% (exclusive) and 45% (5760–5763) — see "risk that changes based on a weak sample" below for why the 45%-win-rate trigger itself is concerning.

## Profit giveback guard

- **FACT.** `GuardOpenProfits` (7083) runs on every tick (called from `OnTick` line 566, unconditionally, before the once-per-bar management gate) and does two independent things: (1) a **profit-lock floor** — once price has covered `InpProfitLockTriggerPercent` (361, default 70%) of the distance to TP, the stop is raised to lock in `InpProfitLockKeepPercent` (362, default 50%) of the *current* open gain (7119–7139); (2) the **giveback guard** proper — once peak R has reached `InpGivebackArmRR` (359, default 1.25R), if the trade's current R falls to or below `peak × (1 − InpMaxProfitGivebackPercent/100)` (360, default 60% giveback), the position is closed outright (7144–7160).

- **COMMENT-CLAIMED, checks out.** V6.32's claim ("giveback guard loosened: 1.25R arm, 60% tolerance, so winners breathe through normal pullbacks") matches the actual default input values (`InpGivebackArmRR=1.25`, `InpMaxProfitGivebackPercent=60.0`) exactly.

## Large number of filters and possible gate contradictions

Every independently-generated candidate signal that is **not** self-confirmed passes through, in this order, inside `SelectBestIndependentSignal` (911–934) — described here as a pipeline of distinct stages, not a literal "five gates ANDed together" (**wording corrected per independent review**: stages 1–2 are hard pass/fail gates, stage 3 can block or merely bench, stages 4–5 modify score rather than gate outright, and the minimum-score/score-gap checks are separate tests applied afterward):
1. `ApplyPremiumDiscountFilter` (1887) — value-area/equilibrium-band gate, with its own four escape hatches.
2. `ApplyConfirmedSupportResistanceGate` (1992) — second-distinct-retest requirement.
3. `ApplyRegimeRouting` (7464) — regime-based block or score adjustment (applies even to self-confirmed setups — see below).
4. `ApplyOrderBlockConfluence` (927/8554) — score modifier only, not a gate.
5. `ApplyLearningToScore` (928/3676) — journal- and regime-based multiplier, capable of forcing the score to exactly `0.0` (line 3727).
Only after all of that does the signal compete against `InpMinimumSignalScore` (70, line 70) and, if both directions have a valid candidate, `InpMinimumScoreGap` (declared line 73, corrected per second-pass review — default 6.0, used at line 895) before either is allowed to trade.

## Risk of strategy score feedback becoming unstable

- **FACT.** Two independent feedback loops exist: (1) `ApplyLearningToScore`'s base-level factor (3676, per-strategy, pooled across regimes, min 8 trades) and (2) its regime-level factor (3711–3739, per-strategy-per-regime, min 10 trades, capable of a hard `0.0` bench). Both multiply into the final score (`factor *= regime_factor`, line 3737), so a strategy that is simultaneously boosted at the base level (winning overall) and boosted again at the regime level (winning in the current regime) can compound both bonuses (up to `(1.18) × (1.20) ≈ 1.42×`) — pushing an already-winning strategy's effective score further above competitors, increasing its selection frequency in `SelectBestIndependentSignal`'s per-direction "highest score wins" comparison (930–933), which in turn feeds it more trades and more data confirming the trend, while a strategy that started with a few early losses gets a compounding *penalty* in the opposite direction and is chosen less often — receiving fewer opportunities to prove itself before its counters have any chance of crossing back over the win-rate midpoint.
- **HYPOTHESIS, mechanism is FACT.** Per the Regime section above, once a strategy is regime-benched (score forced to `0.0`), it structurally cannot win a direction slot in that regime again, and therefore cannot trade there, and therefore cannot update the statistics that would un-bench it — a logical fixed point, not merely a slow decay. Whether real trading data ever drives a strategy into this state, and whether regime reclassification provides a practical escape hatch, requires backtest/live evidence.
- **HYPOTHESIS.** `OverallWinRate()` (6283) — used by `EffectiveATRStopMultiplier`, `EffectiveTrailStartRR`, `EffectiveTrailATRMultiplier`, `EffectiveSoftExitMinimumRR` (5752/6250/6261/6272) — is a single pooled figure across *all three* strategy buckets, so a strategy-specific hot or cold streak within a small sample can swing the EA's *global* stop/trailing behavior for every open position regardless of which strategy or setup produced it. This compounds with the score-feedback loop above (the same small sample simultaneously changes what gets entered *and* how already-open trades are managed).

## Any logic that changes risk based on a weak sample

- **FACT (strongest, most direct answer to this bullet).** The Pilot mechanism (see "Pilot trade and add-ons" above) explicitly permits **higher** actual-equity risk (`InpPilotMaxActualRiskPercent=5.0%`, line 110) on the **single least-confirmed trade** of a fresh trend than the standing risk budget allows for a fully risk-sized, trend-confirmed trade (`InpRiskPercent=1.0%`/`InpMaxRiskPercent=2.0%`, lines 79–80). This is risk *increasing* precisely where confidence is lowest (n=0 confirming trades for this trend so far), which is the inverse of what "changes risk based on sample strength" would normally mean in a risk-management sense.
- **FACT.** `OverallWinRate()` (6283) requires only `InpLearningMinTrades=8` (131) *total, pooled* trades before it starts adjusting stop width and trailing aggressiveness EA-wide (`EffectiveATRStopMultiplier`/`EffectiveTrailStartRR`/`EffectiveTrailATRMultiplier`/`EffectiveSoftExitMinimumRR`). Eight trades is a statistically thin sample — a true 50% win-rate strategy has roughly a 1-in-3 chance of showing ≤37.5% or ≥62.5% wins by chance alone at n=8 — yet crossing the 45%/58% thresholds derived from this sample measurably changes live stop and trailing behavior (5760–5763, 6254–6257, 6265–6268, 6276–6279).
- **FACT.** The per-strategy learning factor (`ApplyLearningToScore`, base level) also activates at `InpLearningMinTrades=8` (line 3690), similarly thin per bucket, though the regime-level layer is more conservative at `InpRegimeLearningMinTrades=10` (137) *per strategy per regime* — a somewhat more defensible (though still small) threshold, and the only one of the two that includes a bench-to-zero safety valve for confirmed-losing combinations (3725–3727).
- **FACT.** `CalculateAllowedRiskCash` (5889) applies `InpAddOnRiskFactor` (118, 0.75×) to the risk budget the moment *any* position is already open (`if(CountOurPositions(_Symbol) > 0) extra_factor *= ...`, line 5911) — this is a sample-independent, always-on de-risking for add-ons (not gated by a weak-sample check), which is a sound design choice and is called out here as a contrast to the pilot-trade risk *increase* above.

## Any conflict between stop floors, stop caps, broker limits, and small-account minimum lots

- **FACT.** Three independent "floor vs. cap vs. broker" mechanisms interact on every trade: (1) `ApplyMinimumStopDistance` (8805, floor = 1.5× M15 ATR, widens only), (2) `GetMaximumStopDistance`/`ApplyStopDistanceCaps` (5863/5820, cap = min of points/percent/ATR caps, rejects or clamps), and (3) `EnsureValidStops` (2988, broker `SYMBOL_TRADE_STOPS_LEVEL`/`SYMBOL_TRADE_FREEZE_LEVEL`/spread padding, widens only) — applied in that literal order inside `OpenSignal` (2704: 2716 → 2718 → 2752).
- **CONTRADICTION (unit mismatch, detailed in the ATR section above).** The ATR-based floor and the percent-of-price cap are not measured in compatible units and are never cross-validated against each other at input-parse or `OnInit` time — nothing in `OnInit` (525) checks whether `InpMinStopDistanceATR × typical-ATR ≤ EffectiveMaxSLPercent × typical-price` for the chart's own symbol, so a misconfigured or naturally-conflicting pair of settings for a given instrument will only be discovered by every single signal being rejected at `ApplyStopDistanceCaps` (unless the elite-score exception at line 5834–5844 applies), silently starving that symbol of trades with no warning beyond a per-rejected-order `Print()`/journal row.
- **FACT.** `IsMinimumLotRiskCompatible` (5807) and `EffectiveMinimumLotActualRiskCapPercent` (5793) provide a *separate*, narrower actual-equity-risk cap specifically for the broker-minimum-lot case (`InpMinimumLotMaxActualRiskPercent=2.00%` global, `InpXAUUSDMinimumLotMaxActualRiskPercent=0.30%` for gold, lines 106–107) — this is distinct from, and *tighter* than, the pilot-trade cap (5.0%, discussed above) even though both paths can independently result in a broker-minimum-lot trade being sent. A pilot trade and a "minimum-lot-compatibility" trade are sized under two different actual-risk ceilings (5.0% vs. 2.0%/0.30%) for what is, from the account's perspective, the identical situation (broker minimum lot forced by account size) — this is a genuine inconsistency in how "the smallest tradeable size is forced on us" is risk-capped depending on *why* it happened (pilot vs. ordinary sizing), verified by comparing lines 2865–2882 (pilot path, cap 110) against lines 5807–5818 (minimum-lot-compatibility path, cap via 5793).
- **HYPOTHESIS.** On a genuinely small account trading a wide-stop instrument (e.g. XAUUSD with the wide-stop profile active, `InpXAUUSDMaxSLATRMultiplier=6.00`, line 103), the broker-minimum-lot's real risk in percent-of-equity terms could routinely exceed even the loosened gold-specific compatibility cap (0.30%, line 107) whenever the ATR floor (1.5× M15 ATR, same for all symbols — there is no XAUUSD-specific override of `InpMinStopDistanceATR`) pushes the structural stop wide. If so, `InpSkipTradeWhenMinLotTooRisky=true` (96, default) would cause the EA to skip essentially all trades on that symbol for that account size — a plausible, code-consistent outcome, but its actual frequency needs live/demo evidence with a real small-account equity curve on a real XAUUSD-quoting broker.

## Completed-candle / repainting check (correction from independent review)

- **CONTRADICTION — BLOCKER, confirmed by independent Codex review, corrects this audit's original conclusion.** This audit originally implied a closed-bar-only conclusion for V6.37 (asserted in the Claude-to-Codex handover as "as both audits concluded"). That blanket conclusion is **false**. Every `CopyRates` array traced in this file is a series array, so logical index `0` is the current, still-forming bar (per official MQL5 `CopyRates` semantics). `IsBullishInsideFalseBreak` (line 6462) and `IsBearishInsideFalseBreak` (line 6470) both read `rates[0].close` — the incomplete bar — and feed `HasBullishCandlePattern`/`HasBearishCandlePattern` (6473–6484), which in turn supply live signal evidence at, among other call sites, lines 1115/1119, 1655/1657, 2364/2370, 2473/2487, 7334/7336, 7618/7634, 7722/7726, 7820/7824, 7977/7999, and 8513/8528. `OnTick` admits one evaluation on a new entry bar (579–580), at which point `rates[0]` is still incomplete — and, on reinitialization mid-bar, both incomplete and already moving. This is not future-candle look-ahead in the classic sense (no data from bars that haven't happened yet is read), but it **is** an intrabar, path-dependent input into a confirmed-pattern decision, which directly violates this project's own completed-candle rule (`PROJECT_RULES.md` #5, master-prompt rule #15). Most other V6.37 structure/fractal paths (BOS/CHoCH, SR, FVG, dealing range) correctly use closed bars and confirmed pivots — this defect is isolated to the false-break candlestick helpers — but it is not cured by the rest of the file being closed-bar-safe, and it must be treated as a release-blocking finding for any new-engine logic derived from this pattern. **Severity: yes — blocks reuse of `IsBullishInsideFalseBreak`/`IsBearishInsideFalseBreak` as written; the rest of the file's closed-bar discipline is unaffected.**

## Netting versus hedging account compatibility (added per independent review)

- **CONTRADICTION/HYPOTHESIS — neither account mode is explicitly handled.** The file never branches on `ACCOUNT_MARGIN_MODE` anywhere (**corrected per second-pass review**: an earlier draft of this section incorrectly referenced a `trade.SetMarginMode()` call as evidence — no such call exists in this file; the point stands without it).
- **On a netting account:** successive same-symbol additions merge into one broker position, so `CountOurPositions` (6700–6715) — the gate `EffectiveMaxPositions` (7543–7551) uses to cap add-ons — stays at 1 regardless of how many add-ons have actually been layered in. The intended 2-add-on cap therefore does not bind on netting accounts. `AddOnConditionsMet` (8058–8100) then measures spacing from the merged, volume-weighted `POSITION_PRICE_OPEN`, not from the last individual add-on's entry. Every add-on also reuses the single merged position ticket, so `StorePositionRiskState` (5965–5994) overwrites the previously-stored aggregate risk/partial-exit/staged-target state on each new add-on while volume sizing only accounts for the newly-added deal — total aggregate exposure is not actually bounded by the intended leg cap under netting.
- **On a hedging account:** `StorePositionRiskState` calls `PositionSelect(_Symbol)` (line 5967) immediately after opening a new position. With more than one open position for the symbol, `PositionSelect` returns the oldest/lowest-ticket position — not necessarily the position that was just opened — so the newly-opened leg can receive no stored risk state while an older leg's state is silently overwritten. It can also select a different position sharing the symbol but a different magic number; the magic check at line 5969 then returns without storing anything for the EA's own new position.
- **Identifier mismatch:** a pending-order fill stores state keyed by `DEAL_POSITION_ID` (lines 697–699), while later management keys off `POSITION_TICKET` (5997–6002) — these identifiers are not guaranteed interchangeable, which is a further hedging-mode risk for the resting-order-limit feature specifically.
- **CONTRADICTION (dormant under shipped defaults, added per second-pass review).** `ClosePartialPosition` (6214–6228) calls `CTrade::PositionClosePartial`, which the official MQL5 documentation defines for hedging-accounting behavior. This path is dormant under the file's shipped defaults (`InpUsePartialTargets=false`, line 345, with staged targets enabled instead), so it does not affect default behavior — but it is a real netting-account incompatibility whenever an operator enables partial-target closes.
- **Severity: HIGH.** Both baselines are materially hedging-oriented in their design assumptions (multiple simultaneous same-symbol positions), but V6.37 has a concrete ticket-association defect that affects even hedging accounts, and its add-on cap is structurally unenforceable on netting accounts. A new engine needs either an explicit, enforced account-mode requirement (reject `OnInit` on the unsupported mode) or genuinely separate netting-safe and hedging-safe position-tracking logic — this cannot be assumed to "just work" on both.

## Trade-submission result handling (added per independent review)

- **CONTRADICTION/FACT.** Both `OpenSignal` (2765–2798, market entries) and the pending-limit path (8769–8781) treat a `true` Boolean return from the `CTrade` method as proof the trade executed, logging the open and updating internal state without checking `ResultRetcode()` or confirming the resulting deal/position actually exists. Per official MQL5 documentation, a `true` result from `CTrade::PositionOpen` only confirms the request was structurally valid — not that the broker executed it. **Severity: depends on evidence, but structurally real** — a requote, partial fill, or delayed rejection could leave the EA's internal state believing a position exists (or exists with different parameters) than what the broker actually holds.

## Broker filling mode, stop/freeze level, and tick-size validation (added per independent review)

- **FACT.** `OnInit` (525–546) sets magic number and deviation but never derives a filling-mode policy from the symbol's actual supported filling flags (no `SetTypeFillingBySymbol`-equivalent call found).
- **FACT.** `EnsureValidStops` (2988–3013) does clamp initial market stops against stop level, freeze level, and spread — but this clamp runs **after** the configured maximum-stop-distance cap is already applied, with no second cap check afterward; the clamp can therefore widen a stop past the policy-configured maximum distance, and the subsequent volume/risk calculation sizes cash risk off that already-widened stop rather than flagging the cap violation.
- **FACT.** Stop-modification logic checks whether a candidate stop is an improvement *before* broker-side clamping is applied, not re-checked afterward — the clamped value can cease to be a genuine improvement over the existing stop.
- **FACT.** Prices are normalized to `_Digits` throughout, not to `SYMBOL_TRADE_TICK_SIZE` — these can differ on instruments with non-decimal tick sizes.
- **FACT.** The resting order-block limit-order path (8715–8771) does not call `EnsureValidStops` at all and only enforces a flat two-point entry-price offset — it does not validate the broker's actual pending-entry stop distance or the attached SL/TP distances against stop/freeze level.
- **FACT.** Both baselines call `OrderCalcMargin` for a margin estimate, but per official documentation this ignores currently open positions and pending orders; neither file performs a final `OrderCheck` before sending a request. **Severity: depends on the specific broker's symbol configuration** — these are real gaps versus "complete broker validation," not confirmed live failures, since the actual impact depends on how far a given broker's real stop/freeze/tick-size values diverge from what the code assumes.

## Restart idempotency and indicator-handle lifecycle (added per independent review)

- **FACT.** New-bar/one-signal-per-bar gating (579–580, 6718–6728) prevents same-bar duplicate signals during continuous runtime, and there is no automatic retry loop on a requote/rejection (it normally just misses that bar's trade rather than duplicating it).
- **HYPOTHESIS (narrowed per second-pass review — not an absolute absence of reconciliation).** Bar/signal stamps are plain volatile globals reset on `OnInit`, and the first tick after a restart is treated as a fresh new bar even if the current bar is already partway through. This is not, however, a complete absence of restart reconciliation: the file does scan existing positions before entering (`CountOurPositions`-based gate, lines 605–607) and does persist/reconcile order-block pending-order tickets across ticks (`SyncOrderBlockLimit`, lines 8662–8673, 8699–8701, 8780–8781). The narrower, accurate defect is that there is no persisted *atomic market-signal/deal identity* and no reliable reconciliation of *ambiguous* submissions — particularly for add-ons layered onto an already-open position — so existing position/order guards prevent many duplicate-entry scenarios but not all of them. Whether this produces actual duplicate entries in practice (versus just a missed bar) needs a live restart-during-signal test, not a code read.
- **FACT.** Indicator handles (ATR/MA/RSI/MACD wrappers, 5929–5945 and 6508–6568) are created and released within each call rather than cached from `OnInit` — no obvious handle leak, but no `BarsCalculated` readiness guard either, and per official documentation `IndicatorRelease` is not actually executed inside the Strategy Tester, so this repeated create/release pattern behaves differently in backtests than live.
- **CONTRADICTION (semantically unsafe fallback, scope corrected per second-pass review — further precision-corrected in fifth-pass review, the two entry paths do not behave identically).** The RSI wrapper falls back to a value of `50` on an invalid handle or failed `CopyBuffer` (lines 6526/6532) — a value that sits at the exact midpoint several of this file's hard-coded RSI comparisons test against. **Phrasing corrected in sixth-pass review** — unlike V811, which declares genuine configurable RSI-window inputs (`InpMomRsiBuyMin/Max`, etc.), V637 declares only RSI *period* inputs (`InpSRRSIPeriod`, `InpTrendRSIPeriod`) and compares against hard-coded literal thresholds directly in the comparison expressions — there is no configurable "acceptance window" in this file, so describing the fallback as sitting inside one overstated what the source actually declares. **`65.0` citation corrected in seventh-pass review** — an earlier draft of this sentence listed `65.0` as one of these hard-coded RSI thresholds; that is false. `65.0` in this file (2482, 2496) is a *signal-score* literal (`tmp.score = 65.0 + ...`), unrelated to any RSI comparison. The actual hard-coded RSI thresholds this file uses are `50.0` (the simple SR checks, 2224/2232, and the inclusive `MomentumStillFavorable` check, 3205/3206), `30.0`/`50.0` (the compound MA-momentum entry expressions, 2670/2685), and `45.0`/`55.0` (the strict `MomentumFailing` branches, 3219–3227). The actual impact on entries is mixed rather than a single "fails" or "passes" answer, and differs by entry path:
  - The simple SR-strategy checks (lines 2224/2232: `rsi1 > 50.0` / `rsi1 < 50.0`) are strict single-sided thresholds — a fallback of *exactly* `50` deterministically **fails** these, since `50 > 50` and `50 < 50` are both false.
  - The MA-momentum (TrendFollowing) checks (lines 2670/2685) are **compound expressions**, not single-sided thresholds: `((rsi2 < 30.0 && rsi1 > 30.0) || rsi1 > 50.0)` for the buy side, mirrored for sell. A fallback does **not** reliably fail this compound check: if `rsi1` falls back to `50` while `rsi2` is a genuinely-read value below 30 (or above 70 for sell), the reversal-cross branch (`rsi2 < 30.0 && rsi1 > 30.0`, true since `50 > 30`) still passes; if only `rsi2` falls back while `rsi1` is genuinely above 50 (or below 50 for sell), the direct branch still passes independent of `rsi2`'s fallback status. Whether a fallback actually passes this compound check therefore depends on which of the two RSI reads failed and what the other one's genuine value was — it is not a blanket pass or fail.

  Separately, the fallback *can* satisfy the more permissive, inclusive RSI subcondition inside `MomentumStillFavorable` (lines 3205/3206), which is used for trade *management* (extension/trailing decisions), not fresh entries. **Additional management-path effect found in third-pass review:** the same `50` fallback also makes both of `MomentumFailing`'s strict branches false (lines 3219–3227) — suppressing that function's momentum-failure exit reason (used at line 3149) rather than triggering it; this exit is `InpExitOnMomentumFailure=false` by default (line 351), so the suppression has no live effect unless an operator has explicitly enabled it.
