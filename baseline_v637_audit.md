## Fractal support and resistance

- **FACT (caller list is illustrative, not exhaustive — "completed" claim from eleventh-pass review corrected in twelfth-pass review; the taxonomy is broader still).** Fractal detection is `IsSwingHigh`/`IsSwingLow` (lines 4844, 4858), a symmetric N-bar-either-side test whose depth is caller-supplied. This caller taxonomy is broader than "three depth inputs" — it includes an unfloored raw-input caller, a fourth timeframe-transformed input, and a hard-coded literal, in addition to the three named inputs. `FindLastTwoSwingIndexes` (4872) and `FindRecentSwingHigh`/`FindRecentSwingLow` (4897, 4905) walk these fractals.
- **FACT.** The actual SR-zone builder is `FindSRZone` (5055–5131). It scores each candidate swing level by: touch count capped/decayed via `InpSRTouchDecayAfter`/`InpSRTouchDecayPenalty` (lines 5099–5103, inputs 252–253), an H4-confluence bonus/penalty via `HasHTFLevelNear` (5107–5111, 7360), a reaction-quality score `SRReactionScore` (5210), a recency term, and a distance penalty (5113). **CONTRADICTION, added thirteenth-pass review:** `HasHTFLevelNear` returns `true` (i.e. confluence found) when no H4 levels or ATR data are available at all (7392–7393) — missing data is treated as *affirmative* H4 confluence and receives the positive bonus, not merely "not penalized." `InpSRMinTouches` (242, default 2) is a hard cutoff (5085–5086). `RefineSRClusterLevel` (5153) re-centers the level on a recency/rejection-weighted average of wick touches rather than the raw first-found fractal (5075–5076 when `InpSRSnapLineToWickCluster` is on).

## Trendline and break-retest logic

- **FACT (count and timeframe corrected in thirteenth-pass review — the twelfth-pass "fixed at both locations" claim was not actually applied here).** There are **three conceptual trendline mechanisms, containing four separate entry implementations**, not one:
  1. `EvaluateSRChannel` (2452) — a rising/falling channel line through the last two swing highs/lows (`FindLastTwoSwingIndexes` + `ProjectLine`), requiring `InpRequireSecondRetest ? 4 : 2` touches (2469, 2477, 2491).
  2. `EvaluateTrendBreaker` (2562) — a "three-point" trendline (`BuildThreePointTrendLine`, 6315) on **`InpTrendHigherTF2`/`InpTrendHigherTF1`** (configurable, defaulting to **M15/H1** at lines 149/148 — **"H1/H4" corrected**; the `desc_h1`/`desc_h4` variable names are just naming, not the actual default timeframes), broken by a 3-candle rule (`ThreeCandleBreak`, 6388) plus MA-cross/MACD/TSMOM confirmation. **Geometry corrected in fourteenth-pass review:** `BuildThreePointTrendLine` (6315–6369) requires three *monotonic* swing prices (older/middle/recent, checked at 6351/6360) but constructs the actual line through only the **older and recent** points (6353–6356, 6362–6365) — the middle swing's distance from that constructed line is never tested, only its monotonic ordering. `EvaluateTrendBreaker` (2582–2614) then projects that line once, at a single fixed time (`exec[1].time`), and `ThreeCandleBreak` (6388–6403) compares every confirmation bar's close against that one constant projected level, not against the line re-projected at each bar's own time. "Three-point trendline" is the source's own naming, but the actual construction and break test are two-anchor-line-plus-constant-level, not a dynamically-projected three-point line.
  3. The dedicated H1 trendline strategies: `BuildTrendlineTouchSignal` (7573) and `BuildTrendlineBreakRetestSignal` (7663) — **two separate implementations**, both built on `BuildThreePointTrendLine(InpTrendlineTF, …)` and grouped as one *mechanism* only because they share that helper.
  This is functioning but duplicated logic — four separate "what is a trendline / has it been touched or broken" implementations across three mechanisms, with different depth inputs, contributing to the file's overall complexity (see "excessive complexity" below).
- **COMMENT-CLAIMED, checks out (corrected in eleventh-pass review — a comment misreading and an incomplete gate description).** Line 314: `InpEnableTrendlineTouch = false // OFF by default per its lifetime journal record`. Verified this is a genuine input default (not a stub) — `BuildTrendlineTouchSignal` is fully implemented (7573–7657). It is gated **twice**, not "only" once: the caller at 814–818 wraps both directions' calls in `if(InpEnableTrendlineTouch)` before ever calling the function, and the function itself repeats the same check via `if(!InpEnableTrendlineTouch) return false;` at 7576 (redundant defensive guard, not the sole gate). The V6.30 comment at lines 7598–7600 explains why the touch requirement was raised: journal showed first-touch entries at a **33–40% win rate** (the comment's own parenthetical — **an earlier draft of this bullet dropped "win rate" and read as "losing 33–40%," which is ambiguous/inaccurate**; a 33–40% win rate is the reason those entries were considered losing propositions, not a claim that 33–40% of trades or capital was lost), so the code now requires `MathMax(3, InpTrendlineMinLineTouches)` (321, default 4) distinct line touches before trading a touch (7601–7606) — this counting is real, done via `CountTrendlineTouches` (7022).
- **FACT.** `BuildTrendlineBreakRetestSignal` (7663) requires `InpTrendlineBreakCloses` (319, default 2) consecutive confirmed-beyond-the-line closes (7690–7709) *before* accepting the current bar as a holding retest (7719–7728), and additionally refuses to trade opposite an H1 regime unless `HasFreshStructureShiftMomentum` fires (7732–7734).

Both the function/input naming and their comments carry a stale "M5" label that does not match the actual configured entry timeframe this function operates on.
- **FACT.** `BuildOBConfluenceSignal` (8477) reuses the FVGRetest strategy bucket (`signal.strategy = "FVGRetest"`, line 8543) for M30-order-block trades, so the journal's per-strategy win-rate learning (`ApplyLearningToScore`) cannot distinguish "plain FVG retest" performance from "M30 OB + SR confluence" performance — both feed the same `g_strategy_wins[STRAT_FVG]`/`g_strategy_trades[STRAT_FVG]` counters (3592–3599, matched by `StringFind(strategy, "FVGRetest")`). ## Journal memory

- **FACT (sharing condition separated in ninth-pass review; `FILE_COMMON` scope corrected in twelfth-pass review).** `EnsureJournalHeader`/`LogJournal` (3419, 3455) write a 44-column CSV (header enumerated at 3440–3450) to `InpJournalFileName` (130, a **configurable** `input string` defaulting to `"ndlovujournal_v637.csv"`) opened with `FILE_COMMON` (3425, 3433, 3475, 3549) — per MQL5's own file-flags documentation, this places the file in the common data folder shared by **every client terminal on the computer** (not only chart/symbol instances of this EA within one terminal), *accessible to* anything opening the same filename there. Whether it is *actually shared* by multiple instances additionally requires those instances to be configured with the same `InpJournalFileName` value — `FILE_COMMON` alone establishes reachability, not that sharing is unconditional. - **COMMENT-CLAIMED, narrowed in tenth-pass review — cross-symbol filtering only, not universal duplicate prevention.** The V6.10 comment (line 676–681, `OnTradeTransaction`) states the journal fixes "duplicate and cross-symbol rows" by checking `deal_symbol != _Symbol` before logging/learning (line 680). It does **not** prevent duplication between two instances attached to the **same** symbol sharing the same `InpMagicNumber` and configured `InpJournalFileName` — both instances receive the same `OnTradeTransaction` event, both pass the magic and symbol checks (672–681), and both would journal/learn from the same deal.
- **CONTRADICTION (journal learning is symbol-scoped, not symbol-and-magic-scoped — added twelfth-pass review).** `OnTradeTransaction`'s live-event filter (672–681) checks both magic number and symbol before logging/learning from a deal. But the 44-column journal header (3440–3450) has **no magic-number field**, and `LoadJournalMemory` (3544–3596) filters replayed rows only by `event_name == "CLOSE"` (3586) and `row_symbol != _Symbol` (3588–3589) — it never checks magic number. Two EA instances on the **same symbol** with **different magic numbers** but the same configured `InpJournalFileName` will each correctly log only their own live events, but on restart each instance's `LoadJournalMemory` will read and learn from **both** instances' historical CLOSE rows, since the file only distinguishes by symbol. This is a separate learning-contamination path from the same-symbol/same-magic live-duplication finding above — it applies even when magic numbers *differ*. `OnTradeTransaction` (line 754) sets `string best_setup = MemorySummary();` and passes this into **both** `LogJournal(...)` (column 16, header-labeled `"BestStrategySetup"`) **and** `UpdateStrategyMemory(strategy, profit, best_setup)` (line 759). `UpdateStrategyMemory` (3623) then does `g_strategy_best_setup[s] = setup` whenever `profit > g_strategy_best_setup_profit[s]` (3648–3651) — meaning the "best setup" slot is populated with a **stringified summary of all three strategies' current best setups**, not the actual per-trade setup name (e.g. `"SR_Bounce"`, `"RANGE_Cycle_Buy"`, `"OB_SR_Confluence_Buy"`) that produced that specific win. Contrast with `OpenSignal` (line 2794), which correctly passes the real `signal.setup` into the *same* CSV column for `"OPEN"` event rows. Because `LoadJournalMemory` (3544) only reads `"CLOSE"` rows (line 3586: `if(event_name != "CLOSE") continue;`) and reads that same column 16 (line 3579: `if(column == 16) setup = value;`) back into `g_strategy_best_setup[s]` on the next restart, the corruption is self-perpetuating across restarts too. Root cause: `EntryDealInfo` (struct, 457–467) has no field to carry the original `signal.setup` string forward from open to close, so `OnTradeTransaction` has no way to recover it and falls back to `MemorySummary()` instead. **Effect:** this does not corrupt the win/loss/profit counters that actually drive score adjustment (`ApplyLearningToScore` only uses `g_strategy_trades`/`g_strategy_wins`/`g_strategy_profit`, not `g_strategy_best_setup`), so it is not a trading-logic bug — but it does corrupt the CSV's `BestStrategySetup` column and the `MemorySummary()` string itself for every *close* event, defeating the intended "which setup wins most" analytics and polluting any downstream (human or Codex/handover) analysis of the journal file.
- **FACT.** `ApplyLearningToScore` (3676) requires `InpLearningMinTrades` (131, default 8) matched trades — pooled across the **entire strategy bucket** (SRBounce/TrendFollowing/FVGRetest, not per individual setup) — before applying any win-rate-derived multiplier (3690–3701), bounded to ±`InpLearningMaxBoostPercent`/`InpLearningMaxPenaltyPercent` (132–133, 18%/14%).
- **CONTRADICTION — `InpUseTradingJournal` and `InpUseJournalLearning` are not operationally independent, added fourteenth-pass review.** `UpdateStrategyMemory` — the function that actually updates the in-memory win/loss/profit counters `ApplyLearningToScore` reads — is called from `OnTradeTransaction` (line 759), which returns immediately at line 662–663 if `InpUseTradingJournal` is `false`. So with the journal disabled but `InpUseJournalLearning` left on, `LoadJournalMemory` can still load whatever memory was saved from a prior session at `OnInit`, and `ApplyLearningToScore` will still apply that stale memory to scoring — but no live trade outcome during the current session ever updates it, since the update path is gated by the journal flag, not the learning flag. An operator turning off only the journal (e.g. to avoid the file-sharing/concurrency risks documented above) silently also freezes the learning system at whatever memory it loaded, without any indication that live learning has stopped.
- **CONTRADICTION — sign-error defect, high severity, added thirteenth-pass review.** The "penalty" branch of the win-rate multiplier (3697–3700) has a sign error that **boosts, rather than penalizes, a strategy with win rate above 50% but net loss**. The boost condition is `win_rate >= 0.50 && g_strategy_profit[s] >= 0.0` (3697); a strategy with `win_rate=0.60` but negative net profit fails this (profit is negative) and falls into the `else` branch (3699–3700): `factor -= InpLearningMaxPenaltyPercent/100.0 * (0.50 - win_rate) * 2.0`. Since `win_rate > 0.50` here, `(0.50 - win_rate)` is **negative**, so `factor -=` a negative quantity **increases** `factor` — a "penalty" that is actually a boost. With the default 14% penalty and a 60% win rate, `factor` gains `0.14 × 0.10 × 2.0 = 0.028` (+2.8%) instead of being reduced. The identical sign error is repeated in the regime-level factor (3729–3733, same structure, default 20% regime penalty — a 60%-regime-win-rate/net-loss bucket gains +4%). At exactly `win_rate=0.50` with net loss, `(0.50-win_rate)=0` so the bucket receives no adjustment at all — a 50%-win/net-loss combination is neither boosted nor penalized. This is a direct arithmetic/control-flow defect in the scoring system this audit's other findings describe as working as designed — a losing-but-high-win-rate strategy (plausible for one with a poor risk/reward ratio: frequent small wins, infrequent large losses) is systematically favored by the exact mechanism meant to demote it.

Whether the floor-vs-cap conflict manifests often enough to matter needs per-symbol backtest data (see the dedicated section below).
- **FACT.** `EffectiveATRStopMultiplier` (5752) widens the ATR multiplier by +0.15 when current ATR exceeds 1.25× its 80-bar average (5757), and by a further +0.10 whenever `OverallWinRate()` sits between 0% (exclusive) and 45% (5760–5763) — see "risk that changes based on a weak sample" below for why the 45%-win-rate trigger itself is concerning.

## Profit giveback guard

- **CONTRADICTION — market-entry R management mixes actual and requested/stored prices, added thirteenth-pass review (the V6.37 analogue of the requested-fill defect documented for V8.11).** `ManageOpenPositions` (3029 area) reads the position's **actual** `POSITION_PRICE_OPEN` (3034, `open_price`) and uses it for the numerator, `open_profit_distance = (current - open_price) * direction` (3049) — but the denominator, `risk` (3042–3043), comes from `GetStoredPositionRisk(ticket)` — the risk distance computed and stored at **signal/submission time** (`abs(entry-sl)` from the requested quote, see `OpenSignal`'s `StorePositionRiskState`, 5965–5976), falling back to `MathAbs(open_price - sl)` only if no stored value exists. If the market entry filled with slippage relative to the requested quote, `rr = open_profit_distance / risk` (3050) divides an actual-price-based numerator by a requested-price-based denominator — the two are not on the same basis, and R (which then drives break-even, trailing, and giveback-guard thresholds) is distorted by the amount of that slippage. The same pattern recurs in the pilot-confirmation loop (6963–6974, `UpdatePilotTrendState`).
- **FACT.** `GuardOpenProfits` (7083) runs on every tick (called from `OnTick` line 566, unconditionally, before the once-per-bar management gate) and does two independent things: (1) a **profit-lock floor** — once price has covered `InpProfitLockTriggerPercent` (361, default 70%) of the distance to TP, the stop is raised to lock in `InpProfitLockKeepPercent` (362, default 50%) of the *current* open gain — **"guaranteed 50%" qualified in fourteenth-pass review**: the candidate stop is checked for improvement at line 7130, but `EnsureValidStops` (7134) can then move it again to satisfy broker minimum-distance rules without a second improvement check against the intended lock level, so the actual locked-in percentage is not guaranteed to be exactly `InpProfitLockKeepPercent` in every case (7119–7139); (2) the **giveback guard** proper — once peak R has reached `InpGivebackArmRR` (359, default 1.25R), if the trade's current R falls to or below `peak × (1 − InpMaxProfitGivebackPercent/100)` (360, default 60% giveback), a close is attempted via `trade.PositionClose` (7157) — **"closed outright" softened in thirteenth-pass review**: the result is not checked before the peak-R key is deleted immediately after (7158), so this is an attempted close, not a guaranteed one (see the peak-R cleanup note below for the same source lines).
- **FACT (cleanup claim corrected in tenth-pass review — it is not universal).** The per-position "peak R" is tracked via a global variable keyed by ticket (`PositionPeakKey`, 7078) and only ever increases (7113–7117), so a position that spikes to 3R and pulls back to 2.9R (a 3.3% giveback, far under the 60% threshold) will not trigger the guard, matching the intended "let winners breathe" design from the V6.32 changelog comment (line 25–26). `GlobalVariableDel(peak_key)` (line 7158, verified as the file's only call site for this key) is reached **only** inside the giveback-guard's own close branch (7144–7160), immediately after `trade.PositionClose(ticket)` — without checking whether that close call actually succeeded. Every other exit path (broker-side SL/TP fill, manual close, time-based exit, or any other `PositionClose` call elsewhere in the file) does **not** delete this key. The accurate statement is that the EA itself does not explicitly delete peak-R keys on any exit path other than the giveback-guard's own close — **"never cleaned up" softened in eleventh-pass review**: per MQL5's own terminal-global-variables documentation, an unaccessed global variable is automatically deleted by the terminal after four weeks, so these keys do not persist forever; they remain stale (not explicitly cleaned up by the EA) until that terminal-level expiry, not indefinitely.
- **COMMENT-CLAIMED, checks out.** V6.32's claim ("giveback guard loosened: 1.25R arm, 60% tolerance, so winners breathe through normal pullbacks") matches the actual default input values (`InpGivebackArmRR=1.25`, `InpMaxProfitGivebackPercent=60.0`) exactly.
- **FACT ("no unresolved ordering question" — reclassified from HYPOTHESIS in thirteenth-pass review; the source settles this, it doesn't just plausibly not-bug it).** The profit-lock floor (item 1 above, `trade.PositionModify` at 7130–7136) executes *before* the giveback block (7144–7158) in `GuardOpenProfits`'s straight-line statement order — there is no branching or async path between them. The giveback predicate reads only `rr` and `peak` (7144, 7147), not `sl`, so the profit-lock's stop modification cannot influence the giveback decision either way. The local `sl` variable is reassigned only after a *successful* modification result (line 7136: `sl = new_sl`), which the giveback branch doesn't consume. This is not merely "in practice sequential, no live bug found by inspection" — the code's explicit statement order and the giveback predicate's specific inputs settle the question directly; there is no unresolved same-pass ordering ambiguity to test for.

## Large number of filters and possible gate contradictions

Every independently-generated candidate signal that is **not** self-confirmed passes through, in this order, inside `SelectBestIndependentSignal` (911–934) — described here as a pipeline of distinct stages, not a literal "five gates ANDed together" (**wording corrected per independent review**: stages 1–2 are hard pass/fail gates, stage 3 can block or merely bench, stages 4–5 modify score rather than gate outright, and the minimum-score/score-gap checks are separate tests applied afterward):
1. `ApplyPremiumDiscountFilter` (1887) — value-area/equilibrium-band gate, with its own four escape hatches.
2. `ApplyConfirmedSupportResistanceGate` (1992) — second-distinct-retest requirement.
3. `ApplyRegimeRouting` (7464) — regime-based block or score adjustment (applies even to self-confirmed setups — see below).
4. `ApplyOrderBlockConfluence` (927/8554) — score modifier only, not a gate.
5. `ApplyLearningToScore` (928/3676) — journal- and regime-based multiplier, capable of forcing the score to exactly `0.0` (line 3727).
Only after all of that does the signal compete against `InpMinimumSignalScore` (70, line 70) and, if both directions have a valid candidate, `InpMinimumScoreGap` (declared line 73, corrected per second-pass review — default 6.0, used at line 895) before either is allowed to trade.

This file's code cannot detect or prevent any of those scenarios.
- **FACT (expanded in tenth-pass review beyond row interleaving alone; the four failure paths were incorrectly generalized as identical — corrected in eleventh-pass review).** Every `FileOpen` call on the journal (`EnsureJournalHeader` 3425/3433, `LogJournal` 3475, `LoadJournalMemory` 3549) omits `FILE_SHARE_READ` and `FILE_SHARE_WRITE` — the flags MQL5's own documentation (`fileflags`/`FileOpen` reference) defines specifically for shared file access across processes/instances. Without them, a second concurrent open attempt on the same file can fail. The four `FileOpen` calls do **not** all fail the same way on `INVALID_HANDLE`: the read probe at 3425 has **no** `INVALID_HANDLE` return at all — if it fails, `need_header` simply stays `true` (its initialized value) and execution falls through to the second, write-mode open at 3433 regardless; a failed read probe can therefore *misclassify* an existing, non-empty file as needing a header, rather than abandoning anything. The three paths that genuinely **do** silently `return`/abandon their operation on `INVALID_HANDLE` are: the write-mode open at 3433–3435 (abandons the header write), `LogJournal` at 3475–3477 (abandons the log row), and `LoadJournalMemory` at 3549–3551 (abandons the memory load) — none of the three print or journal a trace. Separately, `EnsureJournalHeader` (3419–3453) checks emptiness with one handle (3425–3431, closed immediately after), then opens a **second**, independent handle (3433) to append the header if needed — two chart instances initializing at the same moment can each observe the file as empty via their own first handle before either has written a header, and both then append one via their own second handle, producing duplicate header rows.
- **Removed in twelfth-pass review — unsupported hypothesis.** An earlier draft speculated that ordinary concurrent `FileOpen`/`FileWrite`/`FileClose` calls could interleave or corrupt data rows "even where opens succeed." `LogJournal` (3455) issues a single `FileWrite` call per event with no partial-write/multi-call row construction, and nothing in the verified mechanisms (missing share flags, silent open failures, the duplicate-header race) establishes that two successfully-opened writers can corrupt each other's already-complete row writes — that would require an actual concurrent-runtime demonstration, not a plausible-sounding extension of the header-race finding. The verified concurrency risks are the three above (missing `FILE_SHARE_READ`/`FILE_SHARE_WRITE`, silent open failures, and the duplicate-header race); ordinary row interleaving beyond those is not established and is not claimed here. Separately, `FILE_COMMON` (per the official MQL5 file-flags reference) designates the common folder shared by **every client terminal on the computer**, not only chart instances within one terminal — so the actual reachable scope of "instances that could open this same file" is broader than "chart/symbol instances of this EA on one terminal," while still requiring the same configured `InpJournalFileName` to actually collide.

## Risk of strategy score feedback becoming unstable

- **FACT.** Two independent feedback loops exist: (1) `ApplyLearningToScore`'s base-level factor (3676, per-strategy, pooled across regimes, min 8 trades) and (2) its regime-level factor (3711–3739, per-strategy-per-regime, min 10 trades, capable of a hard `0.0` bench). Both multiply into the final score (`factor *= regime_factor`, line 3737), so a strategy that is simultaneously boosted at the base level (winning overall) and boosted again at the regime level (winning in the current regime) can compound both bonuses (up to `(1.18) × (1.20) ≈ 1.42×`) — pushing an already-winning strategy's effective score further above competitors, increasing its selection frequency in `SelectBestIndependentSignal`'s per-direction "highest score wins" comparison (930–933), which in turn feeds it more trades and more data confirming the trend, while a strategy that started with a few early losses gets a compounding *penalty* in the opposite direction and is chosen less often — receiving fewer opportunities to prove itself before its counters have any chance of crossing back over the win-rate midpoint.
- **HYPOTHESIS, mechanism is FACT but narrower than a proven fixed point, and scoped to the ordinary combined-signal pipeline only (see the corrected Regime section above, eleventh-pass review).** Once a strategy is regime-benched (score forced to `0.0`), the actual blocker for *ordinary* candidates is the separate `InpMinimumSignalScore` threshold check (a zero score fails it), not an inability to occupy a direction slot — and the bench does not apply to the NFP-displacement or OB-limit-order entry paths, which bypass `ApplyLearningToScore` entirely (see above). Within the ordinary pipeline, `UpdateStrategyMemory` grades a closing trade by the regime at close time, not the regime it was opened in — so a trade opened elsewhere can still close into, and update, the benched bucket. Under unchanged settings and journal history with no such cross-regime close, and setting the two bypass paths aside, there is no ordinary same-regime entry-driven recovery path for the combined-signal pipeline specifically — but this is not established as a per-strategy lock overall. Whether real trading data ever drives a strategy's ordinary-pipeline entries into an effectively long-lasting bench, and how often cross-regime closes, the bypass paths, or configuration changes actually provide an escape in practice, requires backtest/live evidence.
- **HYPOTHESIS.** `OverallWinRate()` (6283) — used by `EffectiveATRStopMultiplier`, `EffectiveTrailStartRR`, `EffectiveTrailATRMultiplier`, `EffectiveSoftExitMinimumRR` (5752/6250/6261/6272) — is a single pooled figure across *all three* strategy buckets, so a strategy-specific hot or cold streak within a small sample can swing the EA's *global* stop/trailing behavior for every open position regardless of which strategy or setup produced it. This compounds with the score-feedback loop above (the same small sample simultaneously changes what gets entered *and* how already-open trades are managed).

## Any logic that changes risk based on a weak sample

- **FACT (ceiling ratio recomputed in twelfth-pass review, "fresh trend" identity claim removed in fourteenth-pass review — `PilotStage()==0` is symbol/magic state only, not tied to any particular trend, setup, or direction; Rotation-specific compounding added in fourteenth-pass review).** The Pilot mechanism explicitly permits a **looser** actual-equity-risk *ceiling* (`InpPilotMaxActualRiskPercent=5.0%`, line 110) on a stage-0 minimum-lot trade than the EA's implemented cash risk budget (`EffectiveRiskPercent`/`CalculateAllowedRiskCash`, 5773–5780/5889–5913) — **~0.8% of equity for non-XAU symbols and ~0.2% for XAU at shipped defaults, not the raw 1.0%/2.0% input values**, making the ceiling **6.25×/25× the implemented budget under specific runtime conditions (equity≥balance, calm volatility, no news, no open position, and a non-Rotation setup — see below), not a fixed 2.5–5×**. `"5.0%" is a fixed ceiling, but the "least-confirmed trade of a fresh trend" framing overstates what `PilotStage()==0` actually requires — it is symbol/magic-scoped state with no requirement that a new/fresh trend, or any particular setup, is what's occupying that slot (see "Pilot trade and add-ons" above for the full correction). **Rotation setups compound a further reduction:** `OpenSignal` sets `g_rotation_sizing` for any `"ROTATION_"` setup (2754), and `CalculateVolumeForRisk` multiplies the risk-cash budget by `InpRotationRiskFactor` (default 0.75×) *before* the pilot branch (2811–2818) — so a Rotation pilot trade's implemented budget is ~0.6%/~0.15% (non-XAU/XAU), and its ceiling ratio is **8.33×/33.33×**, not 6.25×/25×. Because the pilot is always sized at the broker minimum lot rather than scaled up to that ceiling, its *actual* risk can be below the implemented budget — the supported finding is that the ceiling is loosest exactly where the implemented budget is lowest, not that actual risk is objectively higher on every pilot trade. Pilot trades are also **not limited to occurring once per stored trend**: a losing pilot (stage 1) resets the pilot stage back to 0 (`OnTradeTransaction`, 736–737, only if `InpUseTradingJournal` is on), and a positionless timeout also resets it to 0 (`UpdatePilotTrendState`, 6981–6985) — either way, the *next* qualifying entry at that symbol/magic is again a minimum-lot pilot at the same looser ceiling.
- **FACT.** `OverallWinRate()` (6283) requires only `InpLearningMinTrades=8` (131) *total, pooled* trades before it starts adjusting stop width and trailing aggressiveness EA-wide (`EffectiveATRStopMultiplier`/`EffectiveTrailStartRR`/`EffectiveTrailATRMultiplier`/`EffectiveSoftExitMinimumRR`). Eight trades is a statistically thin sample — **arithmetic corrected in tenth-pass review, then split into two distinct statistics in eleventh-pass review since they answer different questions**: the literal sample-extremity event (≤37.5% or ≥62.5% wins out of 8, i.e. ≤3 or ≥5 wins) has probability 186/256 ≈ **72.7%** for a true 50% win-rate strategy (not the "roughly 1-in-3" an earlier draft claimed — that ~36.3% figure is each one-sided tail alone, not their union). However, the low-side behavior-change branches (5761, 6256, 6267, 6278) all additionally require `win_rate > 0.0` strictly — so the `X=0` case (0 wins out of 8), while counted in the literal ≤3-wins tail, does **not** actually trigger any behavior change. The probability that crossing these thresholds **actually changes live behavior** is therefore the narrower event `X ∈ {1,2,3} ∪ {5,6,7,8}` = 185/256 ≈ **72.3%**, not 72.7%. Use 72.7% only for the literal sample-extremity statistic and 72.3% when concluding that live stop/trailing behavior (5760–5763, 6254–6257, 6265–6268, 6276–6279) actually changes as a result.
- **FACT.** The per-strategy learning factor (`ApplyLearningToScore`, base level) also activates at `InpLearningMinTrades=8` (line 3690), similarly thin per bucket, though the regime-level layer is more conservative at `InpRegimeLearningMinTrades=10` (137) *per strategy per regime* — a somewhat more defensible (though still small) threshold, and the only one of the two that includes a bench-to-zero safety valve for confirmed-losing combinations (3725–3727).
- **FACT (mirror fixed, twelfth-pass review).** `CalculateAllowedRiskCash` (5889) applies `InpAddOnRiskFactor` (118, 0.75×) to the risk budget the moment *any* position is already open (`if(CountOurPositions(_Symbol) > 0) extra_factor *= ...`, line 5911) — this is a sample-independent, always-on de-risking for add-ons (not gated by a weak-sample check), which is a sound design choice and is called out here as a contrast to the pilot-trade's looser risk *ceiling* above (not a guaranteed increase — see the correction there).

## Any conflict between stop floors, stop caps, broker limits, and small-account minimum lots

- **FACT (scope corrected in eleventh-pass review — not literally "every trade").** Three independent "floor vs. cap vs. broker" mechanisms interact on every **market-entry** trade via `OpenSignal`: (1) `ApplyMinimumStopDistance` (8805, floor = 1.5× M15 ATR, widens only), (2) `GetMaximumStopDistance`/`ApplyStopDistanceCaps` (5863/5820, cap = min of points/percent/ATR caps, rejects or clamps), and (3) `EnsureValidStops` (2988, broker `SYMBOL_TRADE_STOPS_LEVEL`/`SYMBOL_TRADE_FREEZE_LEVEL`/spread padding, widens only) — applied in that literal order inside `OpenSignal` (2704: 2716 → 2718 → 2752). The resting-limit path (`SyncOrderBlockLimit`, 8733–8740) applies the floor (1) and its own **inline** cap check using `GetMaximumStopDistance` directly (8738–8740), but does **not** call `EnsureValidStops` or the shared `ApplyStopDistanceCaps` function (3) — it duplicates only the cap comparison, not the full three-mechanism sequence market entries go through (see row 17 in the summary table).
- **CONTRADICTION (recharacterized in tenth-pass review — see the ATR section above for the full correction; visibility distinction sharpened in eleventh-pass review, since the two were previously mixed together).** `ApplyStopDistanceCaps` does compare the floor's resulting stop distance against `GetMaximumStopDistance`'s cap in the same price-distance unit at runtime — they are not "incompatible units, never cross-validated" as an earlier draft of this finding claimed. The actual gap is the absence of any *preflight* check: nothing in `OnInit` (525) confirms, before trading begins, that `InpMinStopDistanceATR × typical-ATR ≤ EffectiveMaxSLPercent × typical-price` for the chart's own symbol, so a misconfigured or naturally-conflicting pair of settings for a given instrument will only be discovered by every single signal being rejected at `ApplyStopDistanceCaps` (unless the elite-score exception at line 5834–5844 applies). These are two distinct claims that should not be conflated: there is genuinely **no preflight warning** that a symbol's floor/cap configuration will conflict before trading starts — but each individual market-entry rejection, once it happens, **is** visibly journaled and printed (2718–2724), not silent. Only the resting-limit path's own inline cap check (8738–8740) is silent per-rejection. The accurate framing is "no advance warning of a starvation pattern," not "no warning at all."
- **FACT.** `IsMinimumLotRiskCompatible` (5807) and `EffectiveMinimumLotActualRiskCapPercent` (5793) provide a *separate*, narrower actual-equity-risk cap specifically for the broker-minimum-lot case (`InpMinimumLotMaxActualRiskPercent=2.00%` global, `InpXAUUSDMinimumLotMaxActualRiskPercent=0.30%` for gold, lines 106–107) — this is distinct from, and *tighter* than, the pilot-trade cap (5.0%, discussed above) even though both paths can independently result in a broker-minimum-lot trade being sent. A pilot trade and a "minimum-lot-compatibility" trade are sized under two different actual-risk ceilings (5.0% vs. 2.0%/0.30%) for what is, from the account's perspective, the identical situation (broker minimum lot forced by account size) — this is a genuine inconsistency in how "the smallest tradeable size is forced on us" is risk-capped depending on *why* it happened (pilot vs. ordinary sizing), verified by comparing lines 2865–2882 (pilot path, cap 110) against lines 5807–5818 (minimum-lot-compatibility path, cap via 5793).
- **HYPOTHESIS.** On a genuinely small account trading a wide-stop instrument (e.g. XAUUSD with the wide-stop profile active, `InpXAUUSDMaxSLATRMultiplier=6.00`, line 103), the broker-minimum-lot's real risk in percent-of-equity terms could routinely exceed even the loosened gold-specific compatibility cap (0.30%, line 107) whenever the ATR floor (1.5× M15 ATR, same for all symbols — there is no XAUUSD-specific override of `InpMinStopDistanceATR`) pushes the structural stop wide. If so, `InpSkipTradeWhenMinLotTooRisky=true` (96, default) would cause the EA to skip essentially all trades on that symbol for that account size — a plausible, code-consistent outcome, but its actual frequency needs live/demo evidence with a real small-account equity curve on a real XAUUSD-quoting broker.

## Completed-candle / repainting check (correction from independent review)

- **CONTRADICTION — BLOCKER, confirmed by independent Codex review, corrects this audit's original conclusion.** This audit originally implied a closed-bar-only conclusion for V6.37 (asserted in the Claude-to-Codex handover as "as both audits concluded"). That blanket conclusion is **false**. Every `CopyRates` array traced in this file is a series array, so logical index `0` is the current, still-forming bar (per official MQL5 `CopyRates` semantics). `IsBullishInsideFalseBreak` (line 6462) and `IsBearishInsideFalseBreak` (line 6470) both read `rates[0].close` — the incomplete bar — and feed `HasBullishCandlePattern`/`HasBearishCandlePattern` (6473–6484), which in turn supply live signal evidence at, among other call sites, lines 1115/1119, 1655/1657, 2364/2370, 2473/2487, 7334/7336, 7618/7634, 7722/7726, 7820/7824, 7977/7999, and 8513/8528. `OnTick` admits one evaluation on a new entry bar (579–580), at which point `rates[0]` is still incomplete — and, on reinitialization mid-bar, both incomplete and already moving. This is not future-candle look-ahead in the classic sense (no data from bars that haven't happened yet is read), but it **is** an intrabar, path-dependent input into a confirmed-pattern decision, which directly violates this project's own completed-candle rule (`PROJECT_RULES.md` #5, master-prompt rule #15). Most other V6.37 structure/fractal paths (BOS/CHoCH, SR, FVG, dealing range) correctly use closed bars and confirmed pivots — this defect is isolated to the false-break candlestick helpers — but it is not cured by the rest of the file being closed-bar-safe, and it must be treated as a release-blocking finding for any new-engine logic derived from this pattern. **Severity: yes — blocks reuse of `IsBullishInsideFalseBreak`/`IsBearishInsideFalseBreak` as written; the rest of the file's closed-bar discipline is unaffected.**

## Netting versus hedging account compatibility (added per independent review)

- **CONTRADICTION/HYPOTHESIS — neither account mode is explicitly handled.** The file never branches on `ACCOUNT_MARGIN_MODE` anywhere (**corrected per second-pass review**: an earlier draft of this section incorrectly referenced a `trade.SetMarginMode()` call as evidence — no such call exists in this file; the point stands without it).
- **On a netting account:** successive same-symbol additions merge into one broker position, so `CountOurPositions` (6700–6715) — the gate `EffectiveMaxPositions` (7543–7551) uses to cap add-ons — stays at 1 regardless of how many add-ons have actually been layered in. The intended 2-add-on cap therefore does not bind on netting accounts. `AddOnConditionsMet` (8058–8100) then measures spacing from the merged, volume-weighted `POSITION_PRICE_OPEN`, not from the last individual add-on's entry. Every add-on also reuses the single merged position ticket, so `StorePositionRiskState` (5965–5994) overwrites the previously-stored aggregate risk/partial-exit/staged-target state on each new add-on while volume sizing only accounts for the newly-added deal — total aggregate exposure is not actually bounded by the intended leg cap under netting.
- **On a hedging account:** `StorePositionRiskState` calls `PositionSelect(_Symbol)` (line 5967) immediately after opening a new position. With more than one open position for the symbol, `PositionSelect` returns the oldest/lowest-ticket position — not necessarily the position that was just opened — so the newly-opened leg can receive no stored risk state while an older leg's state is silently overwritten. It can also select a different position sharing the symbol but a different magic number; the magic check at line 5969 then returns without storing anything for the EA's own new position.
- **Identifier mismatch:** a pending-order fill stores state keyed by `DEAL_POSITION_ID` (lines 697–699), while later management keys off `POSITION_TICKET` (5997–6002) — these identifiers are not guaranteed interchangeable, which is a further hedging-mode risk for the resting-order-limit feature specifically.
- **CONTRADICTION (dormant under shipped defaults, added per second-pass review).** `ClosePartialPosition` (6214–6228) calls `CTrade::PositionClosePartial`, which the official MQL5 documentation defines for hedging-accounting behavior. This path is dormant under the file's shipped defaults (`InpUsePartialTargets=false`, line 345, with staged targets enabled instead), so it does not affect default behavior — but it is a real netting-account incompatibility whenever an operator enables partial-target closes.
- **Severity: HIGH.** Both baselines are materially hedging-oriented in their design assumptions (multiple simultaneous same-symbol positions), but V6.37 has a concrete ticket-association defect that affects even hedging accounts, and its add-on cap is structurally unenforceable on netting accounts. A new engine needs either an explicit, enforced account-mode requirement (reject `OnInit` on the unsupported mode) or genuinely separate netting-safe and hedging-safe position-tracking logic — this cannot be assumed to "just work" on both.

## Trade-submission result handling (added per independent review)

- **CONTRADICTION/FACT.** Both `OpenSignal` (2765–2798, market entries) and the pending-limit path (8769–8781) treat a `true` Boolean return from the `CTrade` method as proof the trade executed, logging the open and updating internal state without checking `ResultRetcode()` or confirming the resulting deal/position actually exists. Per official MQL5 documentation, a `true` result from `CTrade::PositionOpen` only confirms the request was structurally valid — not that the broker executed it. **Severity: depends on evidence, but structurally real** — a requote, partial fill, or delayed rejection could leave the EA's internal state believing a position exists (or exists with different parameters) than what the broker actually holds.

## Broker filling mode, stop/freeze level, and tick-size validation (added per independent review)

- **FACT.** `OnInit` (525–546) sets magic number and deviation but never derives a filling-mode policy from the symbol's actual supported filling flags (no `SetTypeFillingBySymbol`-equivalent call found).
- **FACT.** `EnsureValidStops` (2988–3013) does clamp initial market stops against stop level, freeze level, and spread — but this clamp runs **after** the configured maximum-stop-distance cap is already applied, with no second cap check afterward; the clamp can therefore widen a stop past the policy-configured maximum distance, and the subsequent volume/risk calculation sizes cash risk off that already-widened stop rather than flagging the cap violation.
- **FACT.** Stop-modification logic checks whether a candidate stop is an improvement *before* broker-side clamping is applied, not re-checked afterward — the clamped value can cease to be a genuine improvement over the existing stop.
- **FACT.** Prices are normalized to `_Digits` throughout, not to `SYMBOL_TRADE_TICK_SIZE` — these can differ on instruments with non-decimal tick sizes.
- **FACT.** The resting order-block limit-order path (8715–8771) does not call `EnsureValidStops` at all and only enforces a flat two-point entry-price offset — it does not validate the broker's actual pending-entry stop distance or the attached SL/TP distances against stop/freeze level.
- **FACT.** Both baselines call `OrderCalcMargin` for a margin estimate, but per official documentation this ignores currently open positions and pending orders; neither file performs a final `OrderCheck` before sending a request. **Severity: depends on the specific broker's symbol configuration** — these are real gaps versus "complete broker validation," not confirmed live failures, since the actual impact depends on how far a given broker's real stop/freeze/tick-size values diverge from what the code assumes.

## Restart idempotency and indicator-handle lifecycle (added per independent review)

- **FACT.** New-bar/one-signal-per-bar gating (579–580, 6718–6728) prevents same-bar duplicate signals during continuous runtime, and there is no automatic retry loop on a requote/rejection (it normally just misses that bar's trade rather than duplicating it).
- **HYPOTHESIS (narrowed per second-pass review — not an absolute absence of reconciliation).** Bar/signal stamps are plain volatile globals reset on `OnInit`, and the first tick after a restart is treated as a fresh new bar even if the current bar is already partway through. This is not, however, a complete absence of restart reconciliation: the file does scan existing positions before entering (`CountOurPositions`-based gate, lines 605–607) and does persist/reconcile order-block pending-order tickets across ticks (`SyncOrderBlockLimit`, lines 8662–8673, 8699–8701, 8780–8781). The narrower, accurate defect is that there is no persisted *atomic market-signal/deal identity* and no reliable reconciliation of *ambiguous* submissions — particularly for add-ons layered onto an already-open position — so existing position/order guards prevent many duplicate-entry scenarios but not all of them. Whether this produces actual duplicate entries in practice (versus just a missed bar) needs a live restart-during-signal test, not a code read.
- **FACT.** Indicator handles (ATR/MA/RSI/MACD wrappers, 5929–5945 and 6508–6568) are created and released within each call rather than cached from `OnInit` — no obvious handle leak, but no `BarsCalculated` readiness guard either, and per official documentation `IndicatorRelease` is not actually executed inside the Strategy Tester, so this repeated create/release pattern behaves differently in backtests than live.
- **CONTRADICTION (semantically unsafe fallback, scope corrected per second-pass review — further precision-corrected in fifth-pass review, the two entry paths do not behave identically).** The RSI wrapper falls back to a value of `50` on an invalid handle or failed `CopyBuffer` (lines 6526/6532) — a value that sits at the exact midpoint several of this file's hard-coded RSI comparisons test against. **Phrasing corrected in sixth-pass review** — unlike V811, which declares genuine configurable RSI-window inputs (`InpMomRsiBuyMin/Max`, etc.), V637 declares only RSI *period* inputs (`InpSRRSIPeriod`, `InpTrendRSIPeriod`) and compares against hard-coded literal thresholds directly in the comparison expressions — there is no configurable "acceptance window" in this file, so describing the fallback as sitting inside one overstated what the source actually declares. **`65.0` citation corrected in seventh-pass review** — an earlier draft of this sentence listed `65.0` as one of these hard-coded RSI thresholds; that is false. `65.0` in this file (2482, 2496) is a *signal-score* literal (`tmp.score = 65.0 + ...`), unrelated to any RSI comparison. The actual hard-coded RSI thresholds this file uses are `50.0` (the simple SR checks, 2224/2232, and the inclusive `MomentumStillFavorable` check, 3205/3206); `30.0`/`50.0`/`70.0` (the compound MA-momentum entry expressions, 2670/2685 — **`70.0` added in eighth-pass review, an earlier draft's "30.0/50.0" omitted the sell-side threshold despite this same paragraph correctly citing "above 70 for sell" two sentences later**: buy is `(rsi2 < 30.0 && rsi1 > 30.0) || rsi1 > 50.0`, sell is `(rsi2 > 70.0 && rsi1 < 70.0) || rsi1 < 50.0`); and `45.0`/`55.0` (the strict `MomentumFailing` branches, 3219–3227). The actual impact on entries is mixed rather than a single "fails" or "passes" answer, and differs by entry path:
  - The simple SR-strategy checks (lines 2224/2232: `rsi1 > 50.0` / `rsi1 < 50.0`) are strict single-sided thresholds — a fallback of *exactly* `50` deterministically **fails** these, since `50 > 50` and `50 < 50` are both false.
  - The MA-momentum (TrendFollowing) checks (lines 2670/2685) are **compound expressions**, not single-sided thresholds: `((rsi2 < 30.0 && rsi1 > 30.0) || rsi1 > 50.0)` for the buy side, mirrored for sell. A fallback does **not** reliably fail this compound check: if `rsi1` falls back to `50` while `rsi2` is a genuinely-read value below 30 (or above 70 for sell), the reversal-cross branch (`rsi2 < 30.0 && rsi1 > 30.0`, true since `50 > 30`) still passes; if only `rsi2` falls back while `rsi1` is genuinely above 50 (or below 50 for sell), the direct branch still passes independent of `rsi2`'s fallback status. Whether a fallback actually passes this compound check therefore depends on which of the two RSI reads failed and what the other one's genuine value was — it is not a blanket pass or fail.

  Separately, the fallback *can* satisfy the more permissive, inclusive RSI subcondition inside `MomentumStillFavorable` (lines 3205/3206), which is used for trade *management* (extension/trailing decisions), not fresh entries. **Additional management-path effect found in third-pass review:** the same `50` fallback also makes both of `MomentumFailing`'s strict branches false (lines 3219–3227) — suppressing that function's momentum-failure exit reason (used at line 3149) rather than triggering it; this exit is `InpExitOnMomentumFailure=false` by default (line 351), so the suppression has no live effect unless an operator has explicitly enabled it.
