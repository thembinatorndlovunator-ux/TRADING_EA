## M1 BOS retest

**FACT.** `BuildBOSRetest` (1209–1271) scans the `InpEntryTF` (M1) array for a strong-bodied candle (`BodyRatio>=0.55`, 1230/1254) whose close breaks the local `look`-bar high/low (1218, 1227–1230, 1251–1254), then requires the current candle to retest and reject that level with a pin/engulfing pattern (1232–1235, 1256–1259). **Note (not a bug, a design constraint):** direction is *not* derived from the M1 break itself — line 1212 sets `direction = (g_bias != 0) ? g_bias : g_dir30;` before scanning. This means the setup can only ever confirm an M1 BOS that agrees with the H1/M30 hierarchy; it never independently trades an M1-only countertrend BOS. In practice this is redundant with `TradeDirectionOK`, which every other setup also passes through, so it is consistent house style rather than an isolated flaw.

**CONTRADICTION (corrected per independent review) — the scan does not exhaustively check every candidate in its range.** The loop continues past candidates that fail the initial break/body tests, but once it finds the *first* candidate that passes those tests, it returns immediately even if that candidate's retest-confirmation check subsequently fails — it does not continue on to check whether a later, still-in-range candidate would have passed both the break/body test *and* the retest confirmation. A later valid setup can therefore be skipped in favor of an earlier candidate that ultimately doesn't qualify. **Severity: depends on evidence** — reduces the setup's effective signal rate versus what an exhaustive scan would find; whether this materially costs trade opportunities needs backtest evidence.

## Break-even and runner trailing

**FACT (citation corrected in third-pass review: leg-count assignment is line 1389, not 1391 — 1391 resets peak R, a different variable).** `ManageBasket` (1401–1465) moves all legs to break-even (entry + spread cost, 1428–1429) once `rr >= InpBasketBreakEvenAtR` (default 1.0) **or** a leg has already banked (`count < g_basket_legs`, 1425–1426, assignment at 1389). **Qualified per second-pass review, further qualified in third-pass review:** these two conditions only coincide as described under a fairly specific set of circumstances — current input defaults, no operator override that misaligns the TP ladder against `InpBasketBreakEvenAtR`, and (this qualification added in third-pass review) a **fully successful** basket submission, since `OpenBasket`'s leg-opening loop (1368–1392) can itself submit fewer legs than requested if individual leg orders fail partway through — a partially-filled basket changes the effective `g_basket_legs` count from what was originally requested. Under a netting account, `CountOurPositions` collapses to `1` immediately upon opening a multi-leg basket (per "Netting versus hedging" below), so `count < g_basket_legs` (e.g. `1 < 2`) can already be true from the moment the basket opens — well before any leg has genuinely banked at 1.0R — meaning break-even could trigger immediately on a netting account rather than only after the first leg's TP fires.

**CONTRADICTION — runner trail is neutered by the default configuration.** `InpUseRunnerTrail` (85, default true) arms the trailing stop once `g_basket_peak_r >= InpTrailStartR` (default 1.5, line 86; check at 1437–1438) and then trails `InpTrailStepR` (default 0.6) behind the peak (1440–1445). But with the current default 2-leg basket, the *last* leg's own broker-side take-profit is `ladder[1] = 1.5R` — identical to `InpTrailStartR`. The runner-trail stop only begins to arm at the exact R-level where the only remaining leg's hard TP already closes it. There is no leg left open beyond 1.5R for the trailing stop to ever protect further upside on. Under the shipped defaults, `InpUseRunnerTrail=true` is effectively dead code: the "runner" never gets a chance to run past its own TP. This would only start doing anything if a user **lowers** `InpTrailStartR` below 1.5 (wording corrected per independent review — the fix direction is lowering the threshold, not raising it), extends the TP ladder past 1.5R for the last leg used, or increases leg count so a leg survives past 1.5R.

## 45-minute time exit

**FACT (exit description broadened in tenth-pass review — not exhaustive; several further inaccuracies corrected in eleventh-pass review).** `InpMaxHoldMinutes=45` (line 82). Enforced at 1455–1460: `TimeCurrent() - g_basket_time > InpMaxHoldMinutes*60` → `CloseBasket`. Several precisions on this:
  - **Not "checked earlier in `ManageBasket`'s control flow"** (an earlier draft's phrasing implied `ManageBasket` itself evaluates TP fills): take-profits are broker-side orders (`ladder[]` prices set on the trade at open, see "basket entries"/"laddered take profits"), not something `ManageBasket`'s own code path checks or closes.
  - **A leg TP does not necessarily end the basket before 45 minutes**: under the shipped 2-leg default, TP1 filling closes only that one leg; the remaining leg (potentially the runner) stays open and can still reach the 45-minute condition. Only a TP fill (or broker-side SL, giveback, direction-flip, daily lock, or manual close) that removes **all** remaining exposure ends the basket before the timer.
  - **The condition is strict "greater than," evaluated on the next tick**, not an exact minute-45 cutoff — `TimeCurrent() - g_basket_time > InpMaxHoldMinutes*60` fires on whichever tick first observes the elapsed time exceeding the threshold, not at precisely 45:00.
  - **`CloseBasket` (1485–1500) does not check `CTrade` result codes** — it calls `trade.PositionClose(ticket)` for each matching position without confirming the close succeeded, so this path *attempts* to close the basket rather than guaranteeing it is closed.
  - **After a restart with an open basket, this exit is not applied at all**: in-memory `g_basket_dir` resets to 0 on `OnInit` (the restart defect documented elsewhere in this audit), and `ManageBasket`'s own early return at 1416–1417 (`if(g_basket_dir == 0 || g_basket_risk <= 0.0) return;`) means the 45-minute check at 1455–1460 is never reached until a new basket opens.
  `g_basket_time` is set once at basket open (1388) and never renewed per leg, so an intact, uninterrupted-runtime basket — including any still-running runner leg — is force-closed (subject to the caveats above) at 45 minutes regardless of unrealized R, unless another exit closes all remaining exposure first: the giveback guard, a fully-closing TP, the direction-flip exit (`InpExitOnDirectionFlip`, 1462–1464), the daily lock's `CloseBasket` path (`CheckDailyLimits`, 1562–1563), a broker-side SL fill, or a manual close.

**HYPOTHESIS:** whether 45 minutes systematically cuts off otherwise-good trades can't be settled by reading the code — it depends on the empirical distribution of time-to-target for this instrument/timeframe mix, which requires backtest/trade evidence. What is a FACT from the code alone: the exit is a hard wall-clock cutoff with no allowance for trades that are progressing favorably but slowly (e.g., sitting at +0.6R at minute 44 with the giveback guard not yet armed, since giveback only arms at 0.8R peak).

## Peak drawdown lock

**FACT (partially COMMENT-CLAIMED — does not fully check out; "historical worst drawdown" description corrected in fourth-pass review).** The comment at line 271 states "peak-drawdown memory survives restarts," and it is *partially* true: `g_peak_dd` is persisted via `GlobalVariableSet`/`Get` (274–275 read on `OnInit`, 2302–2303 write on new peak, computed as `MathMax` of every `g_current_dd` reading ever observed, lines 2298–2303) and that persisted maximum does survive a restart. **This is not, precisely, "the historical worst-drawdown percentage"** — `g_current_dd` (2294–2296) is itself always computed relative to `g_peak_balance`, whose own basis resets at every restart (see below), so `g_peak_dd` is more accurately the persisted maximum of a series of *session-relative* drawdown readings, not a value guaranteed to equal the true all-time-peak-to-trough drawdown across multiple restarts. **Persistence-condition added in fifth-pass review:** both the `OnInit` load (274) and the `UpdateDrawdownGuard` save (2302) are guarded by `!MQLInfoInteger(MQL_TESTER)`, so none of this persistence happens inside the Strategy Tester — only in live/demo terminal sessions. **However**, the variable actually used to gate new baskets, `g_current_dd` (computed in `UpdateDrawdownGuard`, 2289–2305, gated against in `OnTick` at 315–319), is derived from `g_peak_balance`, and `g_peak_balance` is **not** persisted — it is reset to the *current* account balance on every `OnInit` (line 272: `g_peak_balance = AccountInfoDouble(ACCOUNT_BALANCE);`, unconditional, no restore-from-GlobalVariable path exists for this specific variable).

**CONTRADICTION (restart impact made conditional in third-pass review — not an unconditional reset to ~0%).** If the EA (or terminal) restarts while the account is already in drawdown from some earlier, higher true balance peak, `g_peak_balance` snaps down to whatever the balance is *at restart time*. `g_current_dd` (`UpdateDrawdownGuard`, using balance/equity at 2291–2296) is then computed relative to that freshly-reset peak, not the true historical one — but this does **not** mean it necessarily reads as ~0%: if the account still has open positions floating at a loss at the moment of restart, `g_current_dd` will reflect the gap between the reset peak (=restart-time balance) and current equity, which can still be nonzero. What is unconditionally true is narrower: the *prior, true* peak-balance component of the drawdown calculation is forgotten on every restart, so `g_current_dd` can **understate** the drawdown relative to the account's real historical peak — the degree of understatement depends on how much higher the true prior peak was than the balance at restart time, and is zero only in the special case where they happened to be equal. `g_peak_dd` (the persisted display value) still remembers the highest *session-relative* drawdown reading observed so far regardless of this specific restart — though, per the correction above, that is not the same guarantee as the true all-time-peak-to-trough drawdown across multiple restarts. The hard lock at `InpMaxDrawdownLockPct` (default 10%, line 158) is checked against the understated `g_current_dd`, not the persisted `g_peak_dd`, so a restart during a drawdown period can silently weaken the basis for the lock and let new baskets open when the original, unbroken peak-balance-relative drawdown was still well above the lock threshold. This is a real gap between the stated intent ("survives restarts") and what is actually enforced, but the magnitude is conditional on the specific prior-peak-vs-restart-balance gap, not a blanket reset to zero.

**FACT (recharacterized in tenth-pass review — not a third peak-drawdown definition; condition on balance-vs-equity made explicit in eleventh-pass review, since the 0.8%/0.4% figures only hold in one of two cases).** `RiskBudgetCash` (1505–1514) does **not** compare a drawdown percentage against a threshold and does not reference any *peak* value at all. It computes `risk_base = MathMax(0.0, equity - MathMax(balance, equity) * InpMaxDrawdownPercent / 100)` (1509–1511, **the `MathMax(0.0, ...)` floor clamp omitted from an earlier draft of this note**) — a fixed haircut off whichever of balance/equity is larger, using the **current** balance/equity pair each call, not a remembered high-water mark — then returns `risk_base * pct / 100` where `pct = MathMin(InpRiskPercent, InpMaxRiskPercent)` (1512). With `E` = equity, `B` = balance, and shipped defaults (`InpMaxDrawdownPercent=20`, `InpRiskPercent=1.00`): **if `E >= B`, `RiskBudgetCash = 0.008·E`** (the flat-or-profitable case — `MathMax(B,E)=E`, so `risk_base=0.8E`); **if `B > E`** (account currently underwater), **`RiskBudgetCash/E = 0.01·(1 − 0.2·B/E)`, clamped to zero** once that expression goes negative. The commonly-cited **0.8% of equity (and ~0.4% per default 2-leg split, pre-rounding) is therefore the `E ≥ B` case specifically, not an unconditional shipped-default percentage** — shipped inputs alone do not determine the result; the current balance/equity relationship does too. The budget only reaches zero, in the `E ≥ B` case, around an ~80% balance-to-equity loss, not at the nominal 20% suggested by the input's name. The file has two genuinely peak-based drawdown notions (display-only `g_peak_dd`, persisted outside Strategy Tester; restart-vulnerable `g_current_dd`/`g_peak_balance` gating new baskets) plus this separate, non-peak-based sizing haircut — `RiskBudgetCash` should not be described as a third drawdown-*from-peak* definition, and its apparent mismatch between the `InpMaxDrawdownPercent` name/intent and its actual sizing formula is itself worth flagging as a specification concern.

## Manual session and news filters

**FACT (blank-vs-stale distinction added in eleventh-pass review — they are not the same failure mode).** `SessionOK()` (2310–2319): weekday-only (2314), optional Friday early cutoff (2316), else a simple `hour >= start && hour < end` band (2318) — default `InpUseSessionFilter=false` (160), explicitly commented "keep OFF for 24/7 synthetics; useful on gold." `NewsOK()`/`InNewsWindow()` (2321–2347): up to three manual `HH:MM` text windows (`InpNewsTime1..3`, 166–168, default empty strings), each expanding to `[time - InpNewsMinsBefore, time + InpNewsMinsAfter]` (2345–2346) on the *current calendar day only* — there is no recurring/weekly schedule and no economic-calendar integration. A **blank or syntactically invalid** string (empty, under 4 characters, or missing a colon) is treated as "no window" (2332–2336: returns `false`, i.e., does not block) — this case genuinely provides zero protection. A **stale but syntactically valid** `HH:MM` (e.g., left over from a news event that no longer occurs at that time) is **not** the same failure mode: it is still converted into a real blocking window at that time-of-day on the current calendar day (2339–2346) — it may protect the wrong moment relative to actual news, but it is not zero protection the way a blank/invalid entry is. Default `InpUseNewsFilter=false` (165). Both filters are fully manual and require the operator to keep them current; leaving them enabled with blank/invalid times provides no protection, while leaving them enabled with stale-but-valid times provides misdirected, not absent, protection (a FACT of the code's behavior, not a defect — the design is explicitly "manual windows for real markets," line 165).

## Potential overexposure caused by multiple basket legs

**FACT — single-basket invariant holds.** `CountOurPositions()>0` gate at `OnTick` 307–308 (counts positions matching `InpMagicNumber` and `_Symbol`, 1639–1653) means a second basket cannot open while any leg of the current one is still open, for this symbol+magic combination. Total basket risk is deliberately capped at `RiskBudgetCash()` split across legs on the **normal sizing path** (**qualifier added in tenth-pass review**; see next section for the minimum-lot fallback that can exceed this cap, subject also to volume rounding, fills, slippage, and broker execution) — legs do not compound each other's stop-loss risk on this symbol.

**HYPOTHESIS — cross-symbol/account-level exposure is ungoverned.** `RiskBudgetCash` (1505–1514) sizes off `AccountInfoDouble(ACCOUNT_EQUITY)` **and** `AccountInfoDouble(ACCOUNT_BALANCE)` (**"equity alone" corrected in eleventh-pass review — see the corrected `RiskBudgetCash` note above; both are account-wide values, so the cross-instance conclusion below is unaffected**) — the whole account's balance/equity, not a per-symbol allocation. `InpMagicNumber` (line 48) is a **configurable** `input long` defaulting to `800001` — **"hard-coded" corrected to "configurable" in tenth-pass review**; it is not a hard-coded constant. **Same magic number is not required for this exposure gap, only sufficient for one specific symptom (corrected in eleventh-pass review):** `CountOurPositions`'s own-instance gate is scoped to `InpMagicNumber` *and* `_Symbol` (1639–1653), so two instances with **different** magic numbers on different symbols still independently draw from the same account-wide balance/equity with no awareness of each other — same magic number only additionally means their `CountOurPositions` scopes could collide if also same-symbol, which is a narrower, separate concern. The Boom/Crash-oriented `InpUseBoomCrashFilter`/`DirectionAllowed` logic (1616–1628) makes multi-symbol deployment of this EA family plausible; **this repo's source and Git history do not establish that such deployment is actually common — that framing is a deployment HYPOTHESIS, not a source-supported fact.** If the same EA is attached to more than one chart/symbol simultaneously (whatever the magic-number configuration), each instance independently computes its own risk budget (per the corrected, balance/equity-conditional `RiskBudgetCash` figures above, not an unconditional "1%") with no awareness of the others, so simultaneous baskets across symbols could jointly risk a multiple of the intended per-basket amount. This cannot be confirmed or refuted from this file alone (it depends on how the EA is actually deployed and configured); it requires deployment/backtest evidence.

**HYPOTHESIS — correlated gap/slippage risk across legs.** All legs of a basket share the identical stop price (`sl` computed once, 1294–1310, applied to every leg in the loop at 1376). On spike-prone synthetic instruments (the exact instrument class this EA guards for via `DirectionAllowed`), a single large gap through the shared stop would slip every leg simultaneously and correlated, rather than averaging out — the loss-per-lot model in `LossPerLot` (1516–1527) assumes fills at the requested SL price with no slippage term. Whether this materially changes realized risk vs. the sized 1% budget needs live/backtest evidence with realistic slippage modeling, not just static reading.

## Whether each leg truly shares the intended total risk

**FACT — the core math is correct when the sizing loop finds a valid multi-leg split.** `OpenBasket` (1317–1351): `total_risk_cash = RiskBudgetCash()` is fixed once, then `leg_vol = total_risk_cash / legs / loss_per_lot` (1330), so if all `legs` positions were stopped out together at the shared `sl`, total realized loss ≈ `total_risk_cash` regardless of whether 1, 2, 3, or 4 legs were opened — the risk is genuinely divided by leg count, not multiplied.

**CONTRADICTION — the documented fallback breaks this guarantee, exactly as the prior red-flag note suspected (reachability boundary corrected in eleventh-pass review — the nominal 1.0% input is not the actual boundary).** The `while(legs >= 1)` loop (1328–1334) reduces `legs` until `leg_vol` clears the broker's minimum volume; if even 1 leg's minimum volume is still too large for the budget (`legs` falls to 0), the code does **not** reject the trade outright. Instead (1335–1347) it computes what percentage of equity that one minimum-lot leg would actually risk (`min_risk_pct`, line 1337) and, if that is **≤ `InpMinLotMaxRiskPercent` (default 2.0%, line 66)**, opens a single minimum-lot leg anyway (1345–1346) — even though `InpRiskPercent` (line 62, commented "TOTAL risk per basket") is nominally 1.00%. The fallback's actual reachability boundary is not the nominal 1.0% input, however: under shipped defaults with equity at or above balance, the *implemented* budget (`RiskBudgetCash()`, see correction above) is ~0.8% of equity, not 1.0%, so the fallback becomes reachable once minimum-lot risk exceeds roughly **0.8%**, and can accept up to **2.0%** — up to **2.5×** the implemented flat budget, not simply "double the nominal 1% input." (The documents may still separately note "up to double the nominal 1% input" as a comparison against the comment's stated intent, provided it is clearly distinguished from the implemented budget this fallback actually measures against.) This is a real, reachable code path, not merely a hypothetical — it is the designed fallback, not a bug in the sense of a crash, but it directly contradicts the "TOTAL risk per basket" framing of `InpRiskPercent`.

## Whether a short fixed holding limit cuts good day trades

**HYPOTHESIS (qualified in eleventh-pass review — see the corrected description above for the caveats this section relies on).** As established above, the 45-minute (`InpMaxHoldMinutes`, line 82) exit is a wall-clock condition applied uniformly regardless of how the trade is developing (1455–1460) for an intact, uninterrupted-runtime basket whose remaining exposure a TP hasn't already fully closed, and it is not adaptive to volatility, timeframe, or setup type (a sweep-shift scalp and a momentum breakout get the same 45 minutes). Whether this cuts off trades that would have reached TP2+ given more time is an empirical question the source code cannot answer — it requires trade-level backtest evidence (e.g., distribution of "time to TP" for winning trades vs. 45 minutes, and how many trades were still open and profitable at the 45-minute mark when this exit attempted to close them).

## Whether the global expansion filter blocks the best breakout opportunities

**Verified gate interaction; intent and impact unresolved (label corrected in fifth-pass review from "CONTRADICTION — verified policy/comment conflict," which conflicted with this same finding's classification elsewhere in this document). Opening framing corrected in third-pass review to state the relationship accurately from the outset rather than overclaiming then conceding otherwise.** `g_expansion` is computed once per `InpWorkingTF` bar (M15 by default, input line 52) in `RefreshWorkingChart` (449/453–456): `atr(InpWorkingTF) >= atr_avg(InpWorkingTF,60) * MathMax(1.1, InpExpansionATRFactor)` (default factor 1.8, line 128) — i.e., "volatility on the working timeframe is currently well above its recent average." `OnTick` then applies this as a **blanket stand-aside gate** at lines 340–344: `if(g_expansion) { ...; return; }` — and this check runs *before* `BuildBestSignal` is even called (347). Every setup, with no exception, is unreachable while `g_expansion` is true — including `BuildMomentumBreakout` (2220–2284), which operates on its own `InpMomTF` array (M5 by default, line 142; see "Momentum breakout" section above) and was specifically coded to be *exempt from the location/PD-band gate* (2216–2218, verified above) because its stated purpose (comment 2213–2218: "the ASQ 7-condition momentum breakout... trades expansion beyond value") is to trade price expansion beyond value — a related but **not definitionally identical** concept to the specific, separately-defined `g_expansion` state (working-timeframe ATR crossing a fixed multiple of its own average). The code exempts the breakout setup from one gate (location) explicitly to let it trade expansions, then blocks it completely with a second, blanket gate that fires on a *different*, though related, expansion definition. There is no code path that reconciles these two conditions — the outer `OnTick` return unconditionally wins whenever `g_expansion` is true, confirmed by tracing the control flow — but because the momentum-timeframe (`InpMomTF`, M5 default) and working-timeframe (`InpWorkingTF`, M15 default) expansion conditions are not the same measurement, the setup remains reachable for any `InpMomTF`-scale momentum breakout that occurs while the `InpWorkingTF`-scale expansion flag is false. The finding is therefore: a verified, reachable gate interaction in control flow between two *related but distinct* expansion definitions, with intent and impact unresolved — not a proven policy/comment conflict, and not a setup blocked by exactly the condition it was built to catch. Whether it actually suppresses the setup's *best* opportunities (i.e., whether the biggest `InpMomTF`-scale breakouts disproportionately coincide with `InpWorkingTF`-scale expansion) is an empirical question requiring backtest evidence, not something the static control-flow trace alone settles.

## Whether the H1/M30 direction gate enters too late or rejects valid reversals

**FACT — the `StructureTrend`/H1-bias classifier is structurally lagging by construction, but this is not a universal statement about every reversal-entry path (scope narrowed in eleventh-pass review).** `TradeDirectionOK` (578–584): if H1 has a defined bias (`g_bias != 0`), a trade is only allowed if `direction == g_bias` **and** `g_dir30 != -direction` (581) — an M30 direction opposing the intended trade blocks it outright even if H1 bias is unchanged. `g_bias` comes from `StructureTrend` (398–417), which requires the **last two confirmed swing highs and lows** (via `FindLastTwoSwings`, depth = `InpSwingDepth`=2, line 121) to jointly form a clean HH+HL (bull) or LH+LL (bear) pattern (410–415) — anything else (including a fresh, still-unconfirmed reversal) returns "ranging" (0). Because a swing point only confirms after `InpSwingDepth` bars have printed on both sides of the pivot, and because the pattern needs the *second-most-recent* swing pair to already agree with the most recent, `StructureTrend` cannot register a new trend until well after the actual turn — this is inherent to any last-two-swings structure classifier, not an implementation bug. **However**, `g_dir30` itself (`RefreshDirectionM30`, 429–441) does **not** share this same two-swing-pair lag: it flips on a break beyond just the single most recent opposing swing (`hi_a`/`lo_a`, 434–439), falling back to the slower `StructureTrend`-style `trend` value only when neither a fresh up- nor down-break is detected (440–441). And when H1 bias is neutral (`g_bias == 0`), `TradeDirectionOK` (583) is governed by `g_dir30` alone (`g_dir30 == 0 || g_dir30 == direction`) — meaning M30 *can* lead a reversal entry once H1 has no established bias to lag behind, using the faster single-swing break rather than waiting for a confirmed two-swing-pair H1 reversal.

**HYPOTHESIS.** Whether this lag is severe enough to "reject valid reversals" in a way that costs more than it protects (vs. false-reversal whipsaws it correctly filters out) cannot be determined from the code alone; it requires backtest evidence comparing entries taken under the current gate vs. a faster/looser reversal trigger.

## Whether pattern drawing and trade detection use the same definitions

**FACT — order blocks, FVGs, range boundaries, and PD bands are consistent between drawing and trading.** `DrawZones()` (1896–1926) reads `ActiveOB(1)`/`ActiveOB(-1)` (949–963) and `g_fvg_bull`/`g_fvg_bear` — the exact same accessor and globals every `Build*` trade setup uses (988, 998, 991, 1001, 1132, 1176). `DrawWorkingChart()`'s PD bands and range lines (1819–1891) are drawn from `g_range_high`/`g_range_low`/`g_equilibrium` (1825–1867) — the same globals `BuildSRBounce`, `BuildSweepShift`, and `LocationOK` (586–594) consume. There is one computation per concept, consumed by both the chart and the trade logic.

**CONTRADICTION — the BOS/CHoCH/EQL/EQH marks are drawing-only and use a different structure definition than anything that trades.** `BuildStructureMarks` (487–573) computes its own independent swing-break scan (its own `prior_dir` bookkeeping, its own 12-bar look-back window at lines 503 and 526, its own equal-high/low tolerance check at 548–572 using `InpEqualTolATR`, distinct from `InpClusterTolATR` used by `FindClusterBoundary`). A grep across the whole file confirms `g_marks[]` is written only in `BuildStructureMarks` (487–573) and read only in `DrawWorkingChart`'s mark-drawing loop (1871–1889) — no `Build*` signal function, no direction function (`StructureTrend`, `RefreshDirectionM30`), and no location function (`FindClusterBoundary`) ever reads `g_marks[]`. In other words, the "BOS"/"CHoCH"/"EQL"/"EQH" labels a trader or developer sees on the chart do **not** correspond to what actually drives `g_bias`, `g_dir30`, or the SR/OB/FVG zones the EA trades from — they are a cosmetically-plausible but functionally disconnected second opinion on structure. This matters for anyone visually cross-checking or tuning the EA against the chart: the visual "confirmation" they're reading is not the logic executing trades.

**Completed-candle check on this specific function (confirmed by independent review, no correction needed — recorded here for completeness):** `BuildStructureMarks` does call `IsSwingHigh`/`IsSwingLow` for candidate index `2` (line 498) at swing depth 2, which does read index `0` (the forming bar) as part of that isolated swing test. However, full control-flow tracing shows this has **no output effect**: for candidate `2`, the newer-break loop starts at `j=1` but requires `j>=2` (lines 503/526) before it can register a BOS/CHoCH mark, so the index-`0` read never actually produces a drawn mark; for candidates `3` and older, the swing test no longer reaches index `0` at all; equal-high/low discovery starts at `depth+1`. **Independent-review conclusion: no drawable structure output or trade decision in this file depends on the forming price bar — V8.11's closed-bar/no-repainting conclusion is confirmed correct**, in contrast to V6.37 (see `baseline_v637_audit.md`'s "Completed-candle / repainting check" section, where the false-break candlestick helpers do have a live forming-bar dependency).

## Whether a restart safely reconstructs basket state

**CONTRADICTION — confirmed, and worse than "state is lost until the next basket": management is permanently stuck, not just reset.** Basket-state globals (`g_basket_dir`, `g_basket_entry`, `g_basket_risk`, `g_basket_time`, `g_basket_legs`, `g_basket_be_done`, `g_basket_peak_r`, declared 230–236 with static zero/false initializers) are plain in-memory globals with no `GlobalVariableSet`/file persistence anywhere in the file (only the peak-drawdown percentage is persisted, and only outside Strategy Tester — **qualifier added in sixth-pass review** — via 271–275/2302–2303, both guarded by `!MQLInfoInteger(MQL_TESTER)`; basket state is not persisted under any condition). `OnInit` (255–281) never scans `PositionsTotal()`/`PositionGetTicket()` to reconstruct these from any already-open positions; it only restores trade parameters, filling mode, and the peak-DD scalar, then calls `ResetDailyState()` and `RefreshHierarchy(true)`.

Tracing what actually happens after a restart with an open basket (broker-side positions intact, EA globals reset to zero):
- `ManageBasket()` (1401–1465) runs every tick (called from `OnTick` line 296). `count = CountOurPositions()` is > 0 (real positions exist), so the early-return path for a flat basket (1404–1415) is skipped. But then `if(g_basket_dir == 0 || g_basket_risk <= 0.0) return;` (1416–1417) fires immediately, because both are freshly zeroed — so **no break-even, no runner trail, no giveback guard, no 45-minute time exit, and no direction-flip exit are ever applied to these orphaned positions.**
- The EA also cannot form a fresh basket to "pick up" management, because the entry gate at `OnTick` 307–308 (`if(CountOurPositions() > 0) return;`) blocks all new signal building for as long as the orphaned positions remain open.
- The dashboard (2059–2077) reports `"Basket: flat"` (since `g_basket_dir == 0`), actively misrepresenting the fact that real, unmanaged exposure is still open on the account.

Net effect: a restart while a basket is open does not just "lose management until a fresh cycle" (as the prior structural note put it) — it disables the *dynamic* risk controls (break-even at 1425–1432, runner trail at 1437–1445, giveback exit at 1448–1453, time exit at 1455–1460, direction-flip exit at 1462–1464) for that basket's remaining lifetime, with a dashboard that gives no indication anything is wrong. **Correction per independent review: this is not "every form of protection disappears."** The broker-held SL/TP survives regardless of the EA's in-memory state, and the separate daily-lock path can still invoke `CloseBasket` independent of `ManageBasket`'s early return. **Precision correction, second-pass review:** what survives is the SL/TP *currently* on the broker's books, not necessarily the *original* values submitted at `OpenBasket` time (line 1376) — if break-even or trailing had already modified the stop before the restart occurred, it is that already-modified value that persists, not the initial one. What is lost is specifically the *dynamic* management layer — break-even, trailing, giveback banking, time-boxing, and direction-flip protection — not the position's terminal safety net entirely.

**Recoverability if a restart-reconstruction fix were attempted (per independent review):** MQL5's position-property APIs make a *conservative* fix possible, but exact recovery of the original basket state is lossy:

| Recoverable/derivable from live positions | Not reliably reconstructable after state changes |
|---|---|
| Symbol, magic, direction, live tickets, current volume/count | Original basket risk after any SL has since moved |
| Actual fill prices / current aggregate entry | Historical `g_basket_peak_r` (needed for giveback/trail logic) |
| Earliest remaining position's open time | Original leg count once one or more legs have already closed |
| Current SL/TP and any setup/leg comments | Exact break-even/trail phase and which legs already banked |
| A conservative "an open basket exists" boolean | Exact shared requested entry vs. distinct per-leg fills |

The robust fix is to persist explicit basket metadata (keyed by account/symbol/magic/basket ID) and reconcile it against live positions in `OnInit`, treating position-only recovery as a conservative fail-safe rather than an assumption that it reproduces the original basket exactly.

**Additional restart-reset state not previously catalogued (per independent review):** beyond the basket-management globals, a restart also resets `g_day_baskets` (the daily basket-count cap tracker), the daily-lock/day-start-equity state, `g_last_basket_close`, `g_last_entry_bar`, and `g_last_breakout_fire` — meaning a restart can silently bypass the daily basket cap and the cooldown/one-signal-per-bar markers, not just basket-level dynamic management. Separately, `OnInit` (line 272) unconditionally resets `g_peak_balance` to the current account balance; the *live* drawdown-lock gate (`UpdateDrawdownGuard`, 2289–2305, checked in `OnTick` 315–319) derives `g_current_dd` from `g_peak_balance`, so a restart during an active drawdown period can lose the higher pre-restart peak-balance reference even though the separately-persisted `g_peak_dd` display statistic — **wording corrected in fifth-pass review to match the "Peak drawdown lock" section above, this location repeated the same overclaim** — still remembers the highest *session-relative* drawdown reading observed so far (the persisted maximum of `g_current_dd` values, not a guaranteed true all-time-peak-to-trough maximum, since `g_current_dd`'s own basis resets every restart too). This has no effect when the former peak and current balance happen to be equal, but is a real gap whenever the true peak was higher than the balance at restart time. Persistence itself is also conditional: both the `OnInit` load (line 274) and the `UpdateDrawdownGuard` save (line 2302) are guarded by `!MQLInfoInteger(MQL_TESTER)`, so this persistence does not occur inside the Strategy Tester at all — only in live/demo terminal sessions.

This restart-management gap (dynamic controls lost, several caps/cooldowns resettable, drawdown-lock basis vulnerable) remains the clearest capital-risk-relevant defect found in this review, even with the corrections above.

## Netting versus hedging account compatibility (added per independent review)

- **CONTRADICTION/HYPOTHESIS — neither account mode is explicitly handled.** The file never branches on `ACCOUNT_MARGIN_MODE`.
- **On a netting account:** `OpenBasket` (1283–1399) can submit 1–4 same-symbol legs (default 2), but netting collapses multiple same-symbol positions into one — so `g_basket_legs = opened` (line 1389) can record `2` while `CountOurPositions` (1639–1653) actually returns `1`. The test `count < g_basket_legs` at line 1425 then treats the (netted, single) position as if the first leg had already banked, and can attempt break-even before the intended 1R threshold is genuinely reached. The basket cannot preserve separate TP legs at all under netting — they merge into one net position with one net TP behavior.
- **Additional ownership hazard:** a pre-existing same-symbol net position opened by a *different* magic number (e.g. a different EA or manual trade) is a further merge/ownership risk, since the EA's own-magic position gate may not detect it before submitting a new entry.
- **Severity: HIGH.** Both baselines are materially hedging-oriented in their design assumptions. A new engine needs either an explicit, enforced account-mode requirement or genuinely netting-safe basket semantics — this cannot be assumed to work correctly on both account types as currently written.

## Trade-submission result handling (added per independent review)

## Broker filling mode, stop/freeze level, and tick-size validation (added per independent review)

- **FACT.** Filling-mode selection (lines 261–269) prefers IOC/FOK flags and otherwise falls back to `ORDER_FILLING_RETURN` — but `RETURN` filling is forbidden by the broker for Market Execution-mode symbols. - **FACT.** `StopsLegal` (1630–1636) checks only the absolute entry-to-SL distance — it does not validate direction correctness, TP-side/distance legality, or tick-size alignment.
- **FACT.** `NormalizePrice` normalizes to `_Digits`, not `SYMBOL_TRADE_TICK_SIZE` — can diverge on instruments with non-decimal tick sizes.
- **FACT.** `MoveBasketStops` neither revalidates the new stop against current stop/freeze distance nor checks the modification's result code (see trade-result-handling finding above).
- **FACT.** Neither this file nor V6.37 performs a final `OrderCheck` before sending a request; `OrderCalcMargin` (used by both) is only a margin estimate that, per official documentation, ignores currently open positions and pending orders. **Severity: depends on the specific broker's symbol configuration.**

## Restart idempotency and indicator-handle lifecycle (added per independent review)

- **FACT.** New-M1-bar gating (301–302, 1778–1787) plus a breakout-specific fire stamp (2223–2225) prevent same-bar duplicate signals during continuous runtime.
- **HYPOTHESIS.** This is not restart-safe: bar/signal stamps are volatile globals reset on `OnInit`, and the first tick after a restart is treated as a fresh new bar regardless of whether the current bar was already underway. Combined with the basket-state loss documented above, a restart followed by a quick close/reopen sequence could plausibly re-enter a position the EA had just been managing, though this requires a live restart test to confirm, not just a code read.
- **FACT.** Indicator handles (`GetATR`/`GetAverageATR` 1734–1757, `GetMA`/`GetRSI` 2352–2372) are created and released per call rather than cached — no obvious handle leak, but no `BarsCalculated` readiness guard, and (per official documentation) `IndicatorRelease` does not actually execute inside the Strategy Tester, so backtest and live behavior of this pattern can differ.
- **CONTRADICTION (semantically unsafe fallback, scope corrected in second-pass review — mixed, not blanket).** `GetRSI` returns `50` on an invalid handle or failed `CopyBuffer` (lines 2366/2371) — and `50` sits inside this file's own default RSI acceptance windows. However, RSI is only one of four ANDed conditions (trend + position + momentum + RSI, lines 2208–2209) required to set `g_mom_bull_ok`/`g_mom_bear_ok`, so a fallback of `50` can satisfy the RSI subcondition specifically, but does **not** by itself make the overall momentum flag true — the other three conditions still have to genuinely hold. A data/indicator failure is indistinguishable from a valid neutral RSI reading, but its blast radius is limited to that one subcondition, not the entire multi-condition signal. Same underlying fallback pattern as V6.37's RSI wrapper, with the same "mixed rather than blanket" scope correction applying there too.
