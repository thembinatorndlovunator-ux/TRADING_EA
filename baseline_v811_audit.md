## SMC sweep-and-shift entries

**FACT.** `BuildSweepShift` (972–1061) is the flagship: `InpSweepScore=88.0` (line 99) is the highest base score of any discrete setup, tying it directly to the "Strong" leg tier (`LegsForScore`, score ≥ 88, line 1278). Logic, verified: `TradeDirectionOK`+`LocationOK` gate (975–979) → location check requires price at range boundary, inside an order block, or inside an FVG (982–1005) → liquidity pool = extreme of bars 4..(4+InpSweepLookback) (1007–1012) → sweep = one of the last 3 bars wicks through the pool and closes back inside it (1014–1030) → shift = the entry candle closes beyond the micro high/low of the following `InpShiftLookback` bars with body ratio ≥ 0.50 (1034–1053). `s.sl` is set to the sweep extreme (1059), not to the shift candle — the eventual stop distance is computed later in `OpenBasket` off this raw extreme plus an ATR buffer (1292–1294).

## Clustered SR bounce

**FACT.** `BuildSRBounce` (1064–1121) trades off `g_range_low`/`g_range_high`, which are populated once per M15 bar by `FindClusterBoundary` (599–676), not by `BuildStructureMarks`. `FindClusterBoundary` clusters swing pivots within `atr*InpClusterTolATR` (608), picks the level with the most touches (629–653, tie-break toward the closest level to current price, 645–646), and retires a boundary that has been closed through twice in a row (657–670, `consecutive>=2` at 665). `BuildSRBounce` requires `touches >= InpClusterMinTouches` (1075), a touch-and-reject pattern using pin/engulfing helpers (1081–1082, 1100–1101), and awards +3 if the boundary was swept first (1088–1093, 1107–1112), plus up to +4 for extra touches (1118) and +2 if aligned with H1 bias (1119–1120).

## M15/M5 order blocks

**FACT.** Two-stage as specified: `ScanOB` (695–743) scans `InpWorkingTF` (M15) bars for a down-close/up-close candle followed by a displacement candle closing beyond it (713–718, 728–733), rejecting mitigated blocks (719–722, 734–737) — raw M15 block stored in `g_ob_bull`/`g_ob_bear`. `RefineOne` (758–802) then looks on `InpRefineTF` (M5) *inside the M15 candle's own time window* (`from`/`to`, 761–762) for the precise opposing M5 candle with its own mini-displacement (777–787, 789–799), storing the tighter box in `g_ob_bull_ref`/`g_ob_bear_ref`. `ActiveOB()` (949–963) prefers the M5-refined zone and falls back to the raw M15 zone — this is the single accessor every consumer (trade setups and `DrawZones`) uses, so refinement doesn't silently diverge from what's traded.

## M5 FVG

**FACT.** `ScanFVG` (819–861) operates on `InpRefineTF` (M5, confirmed at line 824). Gap size must clear `MathMax(3*_Point, atr*InpFVGMinGapATR)` (830, 838, 850). The imbalance candle must have body ratio ≥ 0.55 in the gap's direction (839, 851). **COMMENT-CLAIMED, verified true:** the header comment "first return only" (805) and the FVG comment at line 111 ("first return only") are enforced by the `touched` scan (841–843, 853–855) which walks bars between the gap and the present and discards the gap if any bar already retraced into it — so only a still-*untouched* gap is ever returned, and the loop returns on the first (most recent) such gap found (833, ascending `i` = more recent first), matching "fresh, untouched, first return only."

## M1 BOS retest

**FACT.** `BuildBOSRetest` (1209–1271) scans the `InpEntryTF` (M1) array for a strong-bodied candle (`BodyRatio>=0.55`, 1230/1254) whose close breaks the local `look`-bar high/low (1218, 1227–1230, 1251–1254), then requires the current candle to retest and reject that level with a pin/engulfing pattern (1232–1235, 1256–1259). **Note (not a bug, a design constraint):** direction is *not* derived from the M1 break itself — line 1212 sets `direction = (g_bias != 0) ? g_bias : g_dir30;` before scanning. This means the setup can only ever confirm an M1 BOS that agrees with the H1/M30 hierarchy; it never independently trades an M1-only countertrend BOS. In practice this is redundant with `TradeDirectionOK`, which every other setup also passes through, so it is consistent house style rather than an isolated flaw.

## Candlestick confirmations

**FACT.** Pin-bar and engulfing helpers at 1705–1729: `IsBullishPin`/`IsBearishPin` (1705–1717) require wick ≥ 2×body on the rejection side, opposite wick ≤ 15% of range, and a close in the outer 35% of the bar's range — the two are symmetric (`close > low + 0.65*Range` vs `close < low + 0.35*Range`). `IsBullishEngulf`/`IsBearishEngulf` (1719–1729) are simple two-bar body-engulf checks with no minimum size floor (an engulf of two 1-point bodies passes as readily as two full-ATR bodies). These are reused verbatim across `BuildSRBounce`, `BuildOBScalp`, `BuildFVGScalp`, and `BuildBOSRetest` (1081, 1100, 1141, 1153, 1184, 1195, 1233, 1257) — one shared definition, not four reimplementations.

## Momentum breakout

**FACT.** `RefreshMomentum()` (2163–2210) computes an EMA-fast/EMA-slow trend (2182–2183, 2200), a strength tier from EMA separation vs ATR (2193–2195: tier 2 ≥0.6 ATR, tier 1 ≥0.3 ATR, tier 0 ≥0.1 ATR, else −1), an RSI window check (2205–2206), and candle momentum (2203–2204); `g_mom_bull_ok`/`g_mom_bear_ok` require ALL of trend+position+momentum+RSI (2208–2209) and are gated by `tier < InpMomTrendStrength` returning early (2197–2198) before either flag is set.

`BuildMomentumBreakout` (2220–2284) adds the breakout condition itself: close beyond the `InpBreakoutLookback`-bar extreme within an ATR buffer (2247–2248, 2267–2268), fires once per closed engine bar (2223–2225, 2263, 2283), passes `TradeDirectionOK` (2247, 2267), and refuses to fire straight into the clustered range boundary sitting just ahead (2251–2253, 2270–2272).

**COMMENT-CLAIMED, verified true:** the comment at 2216 states the setup is "Deliberately EXEMPT from the premium/discount location gate" — confirmed: `BuildMomentumBreakout` never calls `LocationOK` anywhere in 2220–2284, unlike every other `Build*` setup. This exemption is real.

**CONTRADICTION (see "expansion filter" below):** despite being the one setup explicitly designed to trade volatility expansion, it is still blocked upstream by the blanket `g_expansion` gate in `OnTick` (340–344), which runs before `BuildBestSignal` is ever called.

## Basket entries

**FACT.** `LegsForScore` (1276–1281) maps score→leg count: ≥88 → `InpLegsStrongSignal`, ≥80 → `InpLegsGoodSignal`, else `InpLegsBaseSignal`, all clamped to [1,4] (`ClampInt`, 1814). Current defaults (72–74) are **all 2** — the tiering exists structurally but is currently flat, consistent with the V8.11 comment "raise back to 3-4 only after the wider stops prove out" (line 72) and the header note "baskets default to 2 legs" (line 32). `OpenBasket` (1283–1399) is gated by `CountOurPositions()==0` (enforced upstream at 307–308, not inside `OpenBasket` itself), so only one basket (of 1–4 legs, same direction, same entry price, same stop) can exist at a time per symbol/magic number.

## Laddered take profits

**FACT.** `ladder[0..3]` built at 1362–1366 from `InpTP1R..InpTP4R` (75–78, defaults 1.0/1.5/2.0/2.5), each forced ≥ the previous rung (`MathMax`) so misconfiguration can't invert the ladder. Each leg `i` gets `tp = entry + direction*distance*ladder[i]` (1371). **Design note, not a bug:** with the current default of 2 legs, only `ladder[0]`=1.0R and `ladder[1]`=1.5R are ever used — `InpTP3R`/`InpTP4R` (2.0R/2.5R) are configured but dead until `InpLegs*Signal` is raised above 2, exactly as the V8.11 comment anticipates (line 33: "targets stay at 1.0R / 1.5R").

## Break-even and runner trailing

**FACT.** `ManageBasket` (1401–1465) moves all legs to break-even (entry + spread cost, 1428–1429) once `rr >= InpBasketBreakEvenAtR` (default 1.0) **or** a leg has already banked (`count < g_basket_legs`, 1425–1426, 1391). With current defaults these two conditions coincide (leg 1's own TP sits at exactly 1.0R = `InpBasketBreakEvenAtR`), so they don't diverge in practice.

**CONTRADICTION — runner trail is neutered by the default configuration.** `InpUseRunnerTrail` (85, default true) arms the trailing stop once `g_basket_peak_r >= InpTrailStartR` (default 1.5, line 86; check at 1437–1438) and then trails `InpTrailStepR` (default 0.6) behind the peak (1440–1445). But with the current default 2-leg basket, the *last* leg's own broker-side take-profit is `ladder[1] = 1.5R` — identical to `InpTrailStartR`. The runner-trail stop only begins to arm at the exact R-level where the only remaining leg's hard TP already closes it. There is no leg left open beyond 1.5R for the trailing stop to ever protect further upside on. Under the shipped defaults, `InpUseRunnerTrail=true` is effectively dead code: the "runner" never gets a chance to run past its own TP. This would only start doing anything if a user raises `InpTrailStartR` below 1.5, extends the TP ladder past 1.5R for the last leg used, or increases leg count so a leg survives past 1.5R.

## Giveback guard

**FACT.** Lines 1448–1453: fires when `g_basket_peak_r >= InpGivebackArmR` (default 0.8) and current `rr <= InpGivebackFloorR` (default 0.1), closing the whole basket via `CloseBasket`. Checked *before* the time exit (1455) and the direction-flip exit (1462) in `ManageBasket`'s control flow, so giveback has effective priority over both when several conditions are true on the same tick.

## 45-minute time exit

**FACT.** `InpMaxHoldMinutes=45` (line 82). Enforced at 1455–1460: `TimeCurrent() - g_basket_time > InpMaxHoldMinutes*60` → `CloseBasket`. `g_basket_time` is set once at basket open (1388) and never renewed per leg, so the whole basket — including any still-running runner leg — is force-closed at 45 minutes regardless of unrealized R, unless the giveback guard or a TP fires first.

**HYPOTHESIS:** whether 45 minutes systematically cuts off otherwise-good trades can't be settled by reading the code — it depends on the empirical distribution of time-to-target for this instrument/timeframe mix, which requires backtest/trade evidence. What is a FACT from the code alone: the exit is a hard wall-clock cutoff with no allowance for trades that are progressing favorably but slowly (e.g., sitting at +0.6R at minute 44 with the giveback guard not yet armed, since giveback only arms at 0.8R peak).

## Peak drawdown lock

**FACT (partially COMMENT-CLAIMED — does not fully check out).** The comment at line 271 states "peak-drawdown memory survives restarts," and it is *partially* true: `g_peak_dd` (the historical worst-drawdown percentage) is persisted via `GlobalVariableSet`/`Get` (274–275 read on `OnInit`, 2302–2303 write on new peak) and does survive a restart. **However**, the variable actually used to gate new baskets, `g_current_dd` (computed in `UpdateDrawdownGuard`, 2289–2305, gated against in `OnTick` at 315–319), is derived from `g_peak_balance`, and `g_peak_balance` is **not** persisted — it is reset to the *current* account balance on every `OnInit` (line 272: `g_peak_balance = AccountInfoDouble(ACCOUNT_BALANCE);`, unconditional, no restore-from-GlobalVariable path exists for this specific variable).

**CONTRADICTION:** if the EA (or terminal) restarts while the account is already in drawdown from some earlier, higher true balance peak, `g_peak_balance` snaps down to whatever the balance is *at restart time*, and `g_current_dd` immediately reads as ~0% on the next tick — even though `g_peak_dd` (the persisted display value) still remembers the true historical worst drawdown. The hard lock at `InpMaxDrawdownLockPct` (default 10%, line 158) is checked against the freshly-reset `g_current_dd`, not the persisted `g_peak_dd`, so a restart during a drawdown period silently clears the basis for the lock and can let new baskets open when the original, unbroken peak-balance-relative drawdown was still well above the lock threshold. This is a real gap between the stated intent ("survives restarts") and what is actually enforced.

**Separate note:** `RiskBudgetCash` (1505–1514) implements a *third*, independent drawdown concept — it throttles the position-sizing budget against `InpMaxDrawdownPercent` (default 20%, line 64) using `MathMax(balance, equity)` (1511) computed fresh every call, with no persistence and no relationship to `g_peak_balance` or `g_peak_dd` at all. The file therefore has three non-unified notions of "drawdown from peak" (display-only persisted `g_peak_dd`; restart-vulnerable `g_current_dd`/`g_peak_balance` gating new baskets; and a same-tick `MathMax(balance,equity)` throttle sizing the risk budget) that do not reference each other.

Enforced in `OnTick` at 320–324 (`g_day_baskets >= InpMaxDayBaskets` → stand aside), incremented in `OpenBasket` at line 1392 (once per opened basket, regardless of leg count), reset to 0 daily in `ResetDailyState` (1529–1536, line 1535) which fires when the server-time day boundary changes (`ResetDailyStateIfNeeded`, 1538–1542, using `StartOfDay`, 1790–1796).

## Manual session and news filters

**FACT.** `SessionOK()` (2310–2319): weekday-only (2314), optional Friday early cutoff (2316), else a simple `hour >= start && hour < end` band (2318) — default `InpUseSessionFilter=false` (160), explicitly commented "keep OFF for 24/7 synthetics; useful on gold." `NewsOK()`/`InNewsWindow()` (2321–2347): up to three manual `HH:MM` text windows (`InpNewsTime1..3`, 166–168, default empty strings), each expanding to `[time - InpNewsMinsBefore, time + InpNewsMinsAfter]` (2345–2346) on the *current calendar day only* — there is no recurring/weekly schedule and no economic-calendar integration; a blank string is treated as "no window" (2332: `time_text=="" → return false`, i.e., does not block). Default `InpUseNewsFilter=false` (165). Both filters are fully manual and require the operator to keep them current; leaving them enabled with stale or blank times provides no actual protection (a FACT of the code's behavior, not a defect — the design is explicitly "manual windows for real markets," line 165).

## Potential overexposure caused by multiple basket legs

**FACT — single-basket invariant holds.** `CountOurPositions()>0` gate at `OnTick` 307–308 (counts positions matching `InpMagicNumber` and `_Symbol`, 1639–1653) means a second basket cannot open while any leg of the current one is still open, for this symbol+magic combination. Total basket risk is deliberately capped at `RiskBudgetCash()` split across legs (see next section) — legs do not compound each other's stop-loss risk on this symbol.

**HYPOTHESIS — cross-symbol/account-level exposure is ungoverned.** `RiskBudgetCash` (1505–1514) sizes off `AccountInfoDouble(ACCOUNT_EQUITY)` — the whole account's equity — not a per-symbol allocation. If the same EA (same magic number is even hard-coded as a single constant default, line 48) is attached to more than one chart/symbol simultaneously — plausible given the Boom/Crash-oriented `InpUseBoomCrashFilter`/`DirectionAllowed` logic (1616–1628) that this EA family is commonly run across an index suite — each instance independently computes "1% of current equity" with no awareness of the others, so simultaneous baskets across symbols could jointly risk a multiple of the intended per-basket 1–2%. This cannot be confirmed or refuted from this file alone (it depends on how the EA is actually deployed); it requires deployment/backtest evidence.

**HYPOTHESIS — correlated gap/slippage risk across legs.** All legs of a basket share the identical stop price (`sl` computed once, 1294–1310, applied to every leg in the loop at 1376). On spike-prone synthetic instruments (the exact instrument class this EA guards for via `DirectionAllowed`), a single large gap through the shared stop would slip every leg simultaneously and correlated, rather than averaging out — the loss-per-lot model in `LossPerLot` (1516–1527) assumes fills at the requested SL price with no slippage term. Whether this materially changes realized risk vs. the sized 1% budget needs live/backtest evidence with realistic slippage modeling, not just static reading.

## Whether each leg truly shares the intended total risk

**FACT — the core math is correct when the sizing loop finds a valid multi-leg split.** `OpenBasket` (1317–1351): `total_risk_cash = RiskBudgetCash()` is fixed once, then `leg_vol = total_risk_cash / legs / loss_per_lot` (1330), so if all `legs` positions were stopped out together at the shared `sl`, total realized loss ≈ `total_risk_cash` regardless of whether 1, 2, 3, or 4 legs were opened — the risk is genuinely divided by leg count, not multiplied.

**CONTRADICTION — the documented fallback breaks this guarantee, exactly as the prior red-flag note suspected.** The `while(legs >= 1)` loop (1328–1334) reduces `legs` until `leg_vol` clears the broker's minimum volume; if even 1 leg's minimum volume is still too large for the budget (`legs` falls to 0), the code does **not** reject the trade outright. Instead (1335–1347) it computes what percentage of equity that one minimum-lot leg would actually risk (`min_risk_pct`, line 1337) and, if that is **≤ `InpMinLotMaxRiskPercent` (default 2.0%, line 66)**, opens a single minimum-lot leg anyway (1345–1346) — even though `InpRiskPercent` (line 62, commented "TOTAL risk per basket") is only 1.00%. On instruments/account-size combinations where the broker's minimum lot's natural risk falls between 1% and 2% of equity, this path silently doubles the intended basket risk. This is a real, reachable code path, not merely a hypothetical — it is the designed fallback, not a bug in the sense of a crash, but it directly contradicts the "TOTAL risk per basket" framing of `InpRiskPercent`.

## Whether a short fixed holding limit cuts good day trades

**HYPOTHESIS.** As established above, the 45-minute (`InpMaxHoldMinutes`, line 82) cutoff is a hard wall-clock exit applied uniformly regardless of how the trade is developing (1455–1460), and it is not adaptive to volatility, timeframe, or setup type (a sweep-shift scalp and a momentum breakout get the same 45 minutes). Whether this cuts off trades that would have reached TP2+ given more time is an empirical question the source code cannot answer — it requires trade-level backtest evidence (e.g., distribution of "time to TP" for winning trades vs. 45 minutes, and how many trades were still open and profitable at the 45-minute mark when force-closed).

## Whether the global expansion filter blocks the best breakout opportunities

**CONTRADICTION — this is the sharpest internal inconsistency in the file.** `g_expansion` is computed once per M15 bar in `RefreshWorkingChart` (455–456): `atr(M15) >= atr_avg(M15,60) * MathMax(1.1, InpExpansionATRFactor)` (default factor 1.8, line 128) — i.e., "M15 volatility is currently well above its recent average." `OnTick` then applies this as a **blanket stand-aside gate** at lines 340–344: `if(g_expansion) { ...; return; }` — and this check runs *before* `BuildBestSignal` is even called (347). Every setup, with no exception, is unreachable while `g_expansion` is true — including `BuildMomentumBreakout` (2220–2284), whose entire stated purpose (comment 2213–2218: "the ASQ 7-condition momentum breakout... trades expansion beyond value") is to trade exactly this condition, and which was specifically coded to be *exempt from the location/PD-band gate* for that reason (2216–2218, verified above). The code exempts the breakout setup from one gate (location) explicitly to let it trade expansions, then blocks it completely with a second, blanket gate (the `g_expansion` stand-aside in `OnTick`) that fires on precisely the volatility condition the setup exists to catch. As written, `BuildMomentumBreakout` can only ever fire in the narrow band where M15 ATR is elevated enough to have cleared the setup's own internal breakout/strength thresholds but not yet 1.8× its 60-bar average — i.e., it is structurally starved of the genuine expansion moves it was built for. Severity assessment does not require backtest evidence here; it follows directly from the control flow.

## Whether the H1/M30 direction gate enters too late or rejects valid reversals

**FACT — the gate is structurally lagging by construction.** `TradeDirectionOK` (578–584): if H1 has a defined bias (`g_bias != 0`), a trade is only allowed if `direction == g_bias` **and** `g_dir30 != -direction` (581) — an M30 direction opposing the intended trade blocks it outright even if H1 bias is unchanged. `g_bias` comes from `StructureTrend` (398–417), which requires the **last two confirmed swing highs and lows** (via `FindLastTwoSwings`, depth = `InpSwingDepth`=2, line 121) to jointly form a clean HH+HL (bull) or LH+LL (bear) pattern (410–415) — anything else (including a fresh, still-unconfirmed reversal) returns "ranging" (0). Because a swing point only confirms after `InpSwingDepth` bars have printed on both sides of the pivot, and because the pattern needs the *second-most-recent* swing pair to already agree with the most recent, `StructureTrend` cannot register a new trend until well after the actual turn — this is inherent to any last-two-swings structure classifier, not an implementation bug.

**HYPOTHESIS.** Whether this lag is severe enough to "reject valid reversals" in a way that costs more than it protects (vs. false-reversal whipsaws it correctly filters out) cannot be determined from the code alone; it requires backtest evidence comparing entries taken under the current gate vs. a faster/looser reversal trigger.

## Whether pattern drawing and trade detection use the same definitions

**FACT — order blocks, FVGs, range boundaries, and PD bands are consistent between drawing and trading.** `DrawZones()` (1896–1926) reads `ActiveOB(1)`/`ActiveOB(-1)` (949–963) and `g_fvg_bull`/`g_fvg_bear` — the exact same accessor and globals every `Build*` trade setup uses (988, 998, 991, 1001, 1132, 1176). `DrawWorkingChart()`'s PD bands and range lines (1819–1891) are drawn from `g_range_high`/`g_range_low`/`g_equilibrium` (1825–1867) — the same globals `BuildSRBounce`, `BuildSweepShift`, and `LocationOK` (586–594) consume. There is one computation per concept, consumed by both the chart and the trade logic.

**CONTRADICTION — the BOS/CHoCH/EQL/EQH marks are drawing-only and use a different structure definition than anything that trades.** `BuildStructureMarks` (487–573) computes its own independent swing-break scan (its own `prior_dir` bookkeeping, its own 12-bar look-back window at lines 503 and 526, its own equal-high/low tolerance check at 548–572 using `InpEqualTolATR`, distinct from `InpClusterTolATR` used by `FindClusterBoundary`). A grep across the whole file confirms `g_marks[]` is written only in `BuildStructureMarks` (487–573) and read only in `DrawWorkingChart`'s mark-drawing loop (1871–1889) — no `Build*` signal function, no direction function (`StructureTrend`, `RefreshDirectionM30`), and no location function (`FindClusterBoundary`) ever reads `g_marks[]`. In other words, the "BOS"/"CHoCH"/"EQL"/"EQH" labels a trader or developer sees on the chart do **not** correspond to what actually drives `g_bias`, `g_dir30`, or the SR/OB/FVG zones the EA trades from — they are a cosmetically-plausible but functionally disconnected second opinion on structure. This matters for anyone visually cross-checking or tuning the EA against the chart: the visual "confirmation" they're reading is not the logic executing trades.

## Whether a restart safely reconstructs basket state

**CONTRADICTION — confirmed, and worse than "state is lost until the next basket": management is permanently stuck, not just reset.** Basket-state globals (`g_basket_dir`, `g_basket_entry`, `g_basket_risk`, `g_basket_time`, `g_basket_legs`, `g_basket_be_done`, `g_basket_peak_r`, declared 230–236 with static zero/false initializers) are plain in-memory globals with no `GlobalVariableSet`/file persistence anywhere in the file (only the peak-drawdown percentage is persisted, 271–275/2302–2303 — basket state is not). `OnInit` (255–281) never scans `PositionsTotal()`/`PositionGetTicket()` to reconstruct these from any already-open positions; it only restores trade parameters, filling mode, and the peak-DD scalar, then calls `ResetDailyState()` and `RefreshHierarchy(true)`.

Tracing what actually happens after a restart with an open basket (broker-side positions intact, EA globals reset to zero):
- `ManageBasket()` (1401–1465) runs every tick (called from `OnTick` line 296). `count = CountOurPositions()` is > 0 (real positions exist), so the early-return path for a flat basket (1404–1415) is skipped. But then `if(g_basket_dir == 0 || g_basket_risk <= 0.0) return;` (1416–1417) fires immediately, because both are freshly zeroed — so **no break-even, no runner trail, no giveback guard, no 45-minute time exit, and no direction-flip exit are ever applied to these orphaned positions.**
- The EA also cannot form a fresh basket to "pick up" management, because the entry gate at `OnTick` 307–308 (`if(CountOurPositions() > 0) return;`) blocks all new signal building for as long as the orphaned positions remain open.
- The dashboard (2059–2077) reports `"Basket: flat"` (since `g_basket_dir == 0`), actively misrepresenting the fact that real, unmanaged exposure is still open on the account.

Net effect: a restart while a basket is open does not just "lose management until a fresh cycle" (as the prior structural note put it) — it permanently disables all of the EA's dynamic risk controls for that basket's remaining lifetime, with only the original static SL/TP orders placed at `OpenBasket` time (1376) left to govern the outcome, and a dashboard that gives no indication anything is wrong. This is the single clearest capital-risk-relevant defect found in this review.
